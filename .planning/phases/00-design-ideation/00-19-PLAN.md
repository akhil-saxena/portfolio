<objective>
Specify the four new photo fields and the revived tags, resolve where `description` renders,
and open the 39 alt texts as human content work.

Purpose: the user asked for "option to add title, place, desc, etc" on photos. The current
record carries `id, title, category, tags (EMPTY on all 39), date, exif{6}, urls, order,
dimensions`. Four fields are missing and one is dead. Two of them carry consequences that a
build phase would get wrong if it inferred them: **`place` must stay manual**, because the
pipeline sets `gps: false` deliberately and deriving location would publish precise
coordinates of personal photographs; and **`alt` is not `title`** — "Into The Mist" names a
photo, it does not describe one, and the public gallery ships 39 images with **zero framework
JS**, so alt is the only description a screen reader ever receives.

Output: an amended field catalog, two resolved schema decisions, a 39-row content brief and a
gate that refuses the obvious wrong answers.
</objective>

**2. Add schema decision 6 — the four new photo fields.** Follow the existing numbered-decision
format (1 through 5), and resolve each field rather than listing options:

- **`place`** — string, optional, **MANUAL free text, never derived.** The pipeline sets
  `gps: false` deliberately; location is *stripped*, not missing. Say plainly what deriving it
  would cost: publishing precise coordinates of personal photographs, including the ones taken
  where the photographer lives. This is the one field where the absence of data is a privacy
  decision that already happened, and a future phase reading "place is empty" must not read
  that as "GPS is available and unused".
- **`description`** — string, optional. Prose about the photograph. Subject to the same
  omission rule the EXIF sub-form already carries: an empty `description` renders **nothing**,
  never an em dash.
- **`alt`** — string, **required for every published photo, and separate from `title`.** State
  the reason in the terms that make it non-negotiable: the public gallery ships zero framework
  JS, so there is no interaction that could reveal a description later; alt is the entire
  non-visual experience of 39 images. State the three rules a value must satisfy: it describes
  what is in the frame, it is not a copy of the title, and it does not open with "Image of" or
  "Photo of" (a screen reader already announces the role).
- **`focalPoint`** — string in the same shape Home's peek positions already use (`"50% 25%"`),
  optional, defaulting to `50% 50%`. Cite `home_config.peekPositions` as the existing precedent
  so the two do not diverge into two shapes for one concept.
- **`tags`** — `string[]`, revived, currently empty on all 39.

Also record, in the same decision, that these fields are **specified here and populated in the
sketch fixture only**. Phase 0 writes no production code, so `data/portfolio_images.json` is
**not** edited by this plan and Phase 3's schema module owns the real migration. Say so
explicitly — the fields must not appear in the committed manifest with 39 empty strings, which
would read as a completed migration.

**3. Add schema decision 7 — where `description` renders on the public site.** This is an open
question and it must leave this plan closed. Resolve it as **lightbox only**, with `title` the
only text in the grid, and give the reasoning:

- The masonry grid's rhythm is the design. `00-PUBLIC-DESIGN-NOTES.md` resolution 5 gives
  photographs an edge on charcoal specifically so the frame carries the image; 39 captions
  insert a text column into a photographic composition.
- At class 1 (312px content, `00-RESPONSIVE-CONTRACT.md` §3) a caption under each tile roughly
  doubles tile height on the narrowest class in the matrix, on the longest page on the site.
- The lightbox already hosts EXIF and already has room for prose, so `description` joins an
  existing text region rather than creating one.
- The accessibility path does not depend on this choice, and that is what makes it safe:
  `alt` is delivered on the `<img>` itself and is present in the grid whatever `description`
  does. State that consequence explicitly — **`description` is not a substitute for `alt`, and
  a photo with a good description and no alt is still inaccessible.**

State the override condition: if the grid should carry captions, the peek/masonry height
budgets in `00-RESPONSIVE-CONTRACT.md` §5.3 recompute and the Photos page's scroll length
changes materially. That is a layout decision, not a copy one.

only directory `check-copy-length.mjs` scans, so the two never meet.

- **The three rules** from schema decision 6: describe the frame, do not repeat the title, do
  not open with "Image of" / "Photo of".

  good alt so the difference is visible rather than described. Pick a photo whose title is
  clearly evocative rather than descriptive.

  there is nothing to derive it from and deriving it would be a privacy regression.
- **A note that `tags` is optional and `description` is optional**, but `alt` is required for

Group the rows by category with a count per category, so the writer can work a category at a
sitting rather than facing 39 rows. Print the per-category counts from the script rather than
transcribing them.

**Do not invent any alt text.** Not one row. This is the whole point of the task: an agent
that writes 39 plausible descriptions of photographs it has never seen produces 39 confident
lies about the photographer's own work, and every one of them ships to a screen-reader user as
fact. Every `alt` cell carries `[AKHIL-ALT]` and nothing else.
