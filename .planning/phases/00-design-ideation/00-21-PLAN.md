<task type="auto">
  <name>Task 1: The gutter ladder and the svh body height</name>
  <files>.playground/src/layouts/Public.astro</files>
  <action>
Put `Public.astro` on the contract. Three changes, and one trap that comes with the first.

**1. The four-step gutter ladder on `.pub-shell`.** Replace the unconditional
`padding: 0 var(--space-12)` with the ladder from §3: `--space-4` at classes 1, `--space-6` at
class 2, `--space-8` at classes 3-4, `--space-12` at classes 5-6. Express it as CSS that
re-evaluates on resize — §6 rule 2 forbids any layout that depends on a viewport measurement
taken once, because unfolding a foldable takes the viewport from ~344px to ~841px in one frame
with no reload. No JS width branch, no build-time viewport assumption.

Write the ladder mobile-first with `min-width` steps so the narrowest class is the unstyled
base and each step names the class boundary it crosses in a comment. The `>= 1024` step must
produce exactly the 48px the approved 1440 design was signed off at — §3 keeps that row
deliberately unchanged so nothing a reviewer has already accepted moves.

**2. `.pub-bar`'s negative margin must follow the ladder.** This is the trap. The rule is
`margin: 0 calc(var(--space-12) * -1)` and its entire job is to cancel the shell's gutter so
the `AppBar` reaches the viewport edge. Change the gutter without changing this and the AppBar
over-hangs by 32px at class 1 — which presents as a horizontal scroll, i.e. exactly the R-6
violation task 2 is trying to close, introduced by the fix for it. Drive both off one custom
property (define `--pub-gutter` on `.pub-shell` and step *that*), so the two cannot drift.

**3. `min-height: 100vh` on `body` becomes `100svh`.** §5.1: `100vh` is the large viewport,
the height with the mobile address bar retracted, so at first paint on iOS Safari and Android
Chrome it is taller than what the user can see. It is currently harmless here — it only makes
short pages fill the screen — but it is the wrong unit **in the one place in the codebase that
will be copied from**, and plan 00-22 copies from it to build a landing whose entire job is to
fit the first paint. Use `min-height`, never `height`: content taller than the budget must
overflow *visibly* rather than clip invisibly, because a visible overflow is a failure a
screenshot catches and a clip is one it hides. Comment both halves.

Do not add `dvh` anywhere. §5.1 forbids it on any scroll-transition participant because it
changes *during* the scroll, moving the transition's own target distance mid-gesture.
  </action>

  <name>Task 2: Close /work's horizontal scroll and make the eight Photos filters reachable</name>
  <files>.playground/src/pages/work.astro, .playground/src/pages/photos.astro</files>
  <action>
**`/work` first, and measure before changing anything.** The recorded violation is
`doc=385/344` and `doc=416/390` — 41px and 26px of overflow. Task 1's ladder gives back 64px of
horizontal room at class 1 and 48px at class 2, so it may already be closed. Rebuild, re-run
`node audit15.mjs /work/`, and read the actual numbers.

If overflow remains, find the offending element **in the browser**, not by reading CSS. The
audit script reports document versus viewport width per class; extend it or use a short
Playwright snippet to walk elements whose `getBoundingClientRect().right` exceeds the viewport,
and name the widest offender. Two of this phase's recorded measurements were wrong because a
1px visually-hidden input masked the label that was the real hit area — source reading is how
that happened.

Fix by **reflow, never hide** (R-6). §6 rule 1: every section, every project and every filter
category exists at 344px. A hiring manager reading on a cover screen who cannot see a project
has lost that project, and there is no alternate mobile edition to fall back to. Where
something cannot fit its designed arrangement it changes arrangement, never presence. Do not
reach for `overflow-x: hidden` — that hides the symptom and, on a page with a real overflowing
child, hides content too.

**Then the Photos filter row.** Eight anchors, and at class 1's 312px content a 44px minimum
hit height wraps them to as many as four rows — 176px of a ~800px viewport spent on filters,
which is not acceptable on a cover screen. §2 resolves it:

- **Classes 3-6: the row wraps.** Unchanged behaviour.
- **Classes 1-2: it becomes a horizontal scroll rail with `scroll-snap-type: x proximity`.**

State in a comment why the rail is safe *here* and would not be on Home: the nested-scroll
hazard §5.4 names applies when a horizontal rail sits inside a vertical snap container, and on
iOS such a rail readily steals the vertical gesture. **Photos has no vertical snap container**,
so it does not apply. Home's peek gallery is therefore a grid at every class and never a rail —
same pattern, opposite verdict, and the reason is the container. Writing that down is what
stops the next person copying the rail onto Home.

**The 44px floor goes on the hit area, not on the drawn control.** A 9.5px mono filter pill
grown into a 44px slab is a different design and destroys the editorial identity. Keep the
drawn geometry and reach the floor through padding or an `::after` overlay that extends the
target without extending the paint. Gate it on `@media (pointer: coarse)` — five of the six
classes are coarse, so this is the common case. **Never `any-pointer`**: a tablet with a
keyboard case reports touch as its primary pointer and the user still touches the screen, so
`any-pointer: fine` returns the wrong answer. The contract forbids it for any density purpose.

Keep the existing `prefers-reduced-motion` guard at `photos.astro:361` intact — it is the
precedent the rest of the site follows.
