**`min-height`, never `height`.** Content taller than the budget must overflow *visibly* and
push the prompt down, rather than being clipped invisibly. A visible overflow is a failure a
screenshot catches; a clip is one it hides.

**`svh`, never `vh`, `lvh` or `dvh`.** `100vh` is the large viewport — the height with the
mobile address bar retracted — so at first paint on iOS Safari and Android Chrome it is taller
than what the user can see, which pushes the one element whose entire job is to be seen at
first paint below the fold. `dvh` is forbidden on any scroll-transition participant because it
changes *during* the scroll, moving the transition's own target distance mid-gesture. Comment
the choice; it looks arbitrary and is not.

**Solve the peek grid as a height budget, per class.** All six `peekIds` render at all six
classes — R-6, reflow never hide. Dropping to four on a narrow screen means two of the six
photographs Akhil chose do not exist on that class, and this is a portfolio with no summary
edition to fall back to. Column count and tile aspect are the variables; tile *count* is not.

- Classes 1-2: 2 x 3 at 3:2 is already known to fit with room.
- Class 3 at its narrow end is the binding case. 3 x 2 at 3:2 overflows by ~44px; 16:9 and 2:1
  both fit. Choose one, and choose it by measuring in the browser at 673 x 620 rather than by
  trusting the table — the table's chrome estimate is derived, not measured. Prefer the aspect
  that keeps the most of the photograph while fitting.

**The grid is a grid at every class and never a horizontal rail.** A rail fits any budget, but
it nests a horizontal scroller inside the vertical snap container task 3 adds, and on iOS a

**Add `scroll-snap` as an enhancement over the plain scroll, never as the mechanism.** §5.4
adopts exactly one form: `scroll-snap-type: y proximity` on the page container, with
`scroll-snap-align: start` on the photos section and on the work section — **two snap points,
both reachable** — and the whole block lives **inside**
`@media (prefers-reduced-motion: no-preference)`.

- **`mandatory` is forbidden by the contract.** State B is two sections and is taller than the
  viewport at every class; under `mandatory` the browser can snap back past content the reader
  is trying to reach.
- **Snap is never load-bearing.** Every state reachable with snap is reachable without it. If
  snap were removed entirely the design still meets the user's sentence, because the plain
  document scroll already does. That is the test a snap enhancement has to pass — verify it by
  disabling the block and confirming the page still behaves, before shipping it.

**Reduced motion, four rules.** `scroll-snap-type` lives inside
`prefers-reduced-motion: no-preference` — the non-obvious one, and deliberate: snap converts a
small user gesture into a large involuntary viewport translation, which is the exact class of
motion the preference exists to suppress. `scroll-behavior: smooth` is **opt-in, never
opt-out** — written the other way round the default is animated and the accessible path is the
exception. Any scroll-driven animation on the departing photos block is **disabled entirely**
under reduced motion, not slowed. And user-initiated scrolling itself is exempt and must not be
suppressed: the preference governs motion the page generates, not motion the user performs.
