# Phase 0 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## How to read this document

Phase 0's output *is* design. No production application code is written. So this is **not**
a contract for a feature being built — it is **the visual and editorial contract the Phase 0
sketches must themselves obey**, so that ~35 throwaway artefacts are coherent with each
other and reviewable as a set.

It has three downstream lives:

| Consumer | Uses |
|----------|------|
| Phase 0 planner / executor | §Spacing, §Typography, §Colour, §Density, §Component Mapping, §Review Convention, §Copywriting, §Ivory→Charcoal |
| **Phase 1 (`../design-system`, DS-01…DS-09)** | §Colour is the token contract to implement. §Typography's scale verdict and §Density's measured gaps set scope. |
| **Phase 06.1 (DS-10…DS-12)** | §Density Contract is the target |
| Phase 5 / 6 / 7 | §Typography, §Copywriting, §Component Mapping, §Ivory→Charcoal |

**Derivation policy.** The user answered 45 questions in discuss-phase. This spec asked
**zero** further questions. Every value below is either (a) locked upstream and restated,
(b) measured from a file or a contrast calculation during this session, or (c) derived from
(a) and (b) with the derivation stated inline. Items where a derivation should be reviewed
rather than assumed are collected in §Confirm-or-Override.

## Spacing Scale

**Ownership (D-31, locked).** A brand theme owns colour, typography and geometry accents.
It does **not** own spacing or sizing. The scale below is the design system's, unchanged,
and the charcoal theme must not redefine a single `--space-*` token.

Declared values — the DS's existing 16-step scale, all multiples of 4:

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| `--space-1` | 4px | Icon gaps, chip inner padding, inline label offset |
| `--space-2` | 8px | Compact element spacing, pill gap in the Photos filter row |
| `--space-3` | 12px | Form field internal rhythm |
| `--space-4` | 16px | Default element spacing; Photos masonry column-gap and tile bottom margin |
| `--space-6` | 24px | Card and panel padding; admin form group spacing |
| `--space-8` | 32px | Layout gaps; admin section breaks |
| `--space-10` | 40px | Home Act-2 project grid row gap |
| `--space-12` | 48px | Major section breaks; Work/Photos page horizontal padding |
| `--space-14` | 56px | Home Act-2 project grid column gap |
| `--space-16` | 64px | Page-level vertical spacing |

Intermediate steps `--space-5/7/9/11/13/15` (20/28/36/44/60px) exist and are legal; the ten
above are the ones this phase's sketches actually need.

**Exceptions — three, each with a reason. Nothing else is off-grid.**

1. **44px minimum touch target** on every interactive control in a **phone** layout (D-09),
   expressed as `--space-11`. This is the floor that `data-density="compact"` must never
   cross — see §Density Contract.
2. **14px** photo-grid gap on Home Act 1 (handoff §Act 1, "14px gap"). Not on the 4px grid.
   Snap to `--space-4` (16px) in sketches and record the 2px delta; QUAL-04 judges the built
   site against the handoff, and a 2px gap delta on a 3×2 grid is below the threshold at
   which a reviewer can see it. **Do not introduce a 14px token.**
3. **Button padding `7px 14px`** — hardcoded as an inline style in
   `../design-system/src/inputs/Button/index.tsx`, with a source comment stating the values
   *deliberately* sit off the 4px grid because snapping them would change button height.
   Accept it. Its consequence for density is a measured finding — see G-2.

**Layout maxima (from the handoff, unchanged).** Home 1080px · Work and Photos 1280px ·
admin content column 960px inside `AppShell` · case-study prose measure **68ch**
(derived: at `--text-md` 15px DM Sans, 68ch ≈ 620px, which is the standard 55–75ch
readability band and sits comfortably inside the handoff's 480px-capped sub-paragraph
convention scaled up for long-form body).

## Typography

### Families (theme-owned, D-31)

| Token | Stack | Role |
|-------|-------|------|
| `--font-serif` / `--serif` / `--font-display` / `--display` | `"Playfair Display Variable", "Playfair Display", Georgia, serif` | Display, headings, editorial italics, project names |
| `--font-body` / `--font` | `"DM Sans Variable", "DM Sans", system-ui, sans-serif` | All UI text, body copy, form labels and values |
| `--font-mono` / `--mono` | `"IBM Plex Mono", ui-monospace, SFMono-Regular, Menlo, monospace` | Eyebrows, metadata, counters, status labels, metrics |

**The `Variable` suffix is load-bearing.** Fontsource's variable packages register the
family as `'Playfair Display Variable'` / `'DM Sans Variable'`. A charcoal token that names
only `"Playfair Display"` while `fonts/charcoal.css` declares
`font-family: 'Playfair Display Variable'` **silently renders Georgia**. Both names must
appear in the stack in that order, and `check-font-names.mjs` (VALIDATION.md, Wave 0) must
assert every family named in a `--font-*` token has a matching `@font-face`.

**IBM Plex Mono has no `Variable` alias.** `@fontsource-variable/ibm-plex-mono` returns npm
404 (RESEARCH.md `[VERIFIED]`); only `@fontsource/ibm-plex-mono` static exists. Its stack
therefore correctly names the plain family. Per RESEARCH.md's recommendation, font delivery
uses **Option A** — `fonts/charcoal.css` re-exports the Fontsource CSS entry points
(`playfair-display/wght.css` + `dm-sans/wght.css` + `ibm-plex-mono/latin-400.css` +
`latin-500.css`) for **8 `@font-face` rules**, down from 73. D-30's "latin subset only"
is restated as **"latin-only *download*, guaranteed by `unicode-range`"**.

### Weights (theme-owned)

Charcoal declares **four**: 400, 500, 600, 700.

| Token | Value | Used for |
|-------|-------|----------|
| `--weight-regular` | 400 | Body copy, Playfair display headings at ≥40px, mono metadata |
| `--weight-medium` | 500 | Nav links, form labels, mono eyebrows and metrics |
| `--weight-semibold` | 600 | Reserved for DS component internals (buttons, tabs). **Not used in authored copy.** |
| `--weight-bold` | 700 | Playfair headings below 40px, project names, logo, card titles |
| `--weight-extrabold` | **alias → 700** | Retired for charcoal |
| `--weight-black` | **alias → 700** | Retired for charcoal |

*Derivation:* the handoff uses only 400/500/700 in authored copy. 600 cannot be retired
because DS primitives reference `--weight-semibold` internally and DM Sans Variable renders
it correctly. 800/900 have no place in an editorial serif identity and both families would
synthesise or clamp them, so they alias to 700 rather than being left at DS defaults. They
are still *declared*, because §Colour's exhaustiveness invariant requires every token
declared in the charcoal light block to be restated in the dark block, and retiring by
omission would be the exact failure that invariant exists to catch.

### Scale — the DS scale is the scale, and it has one hole

`--text-*` is **sizing**, therefore **DS-owned** (D-31). Charcoal must not redefine it. This
is the tension RESEARCH.md flagged as needing an explicit resolution (A5), so:

> **Ruling.** `--text-*` is a shared scale owned by the design system. A brand that needs a
> step the scale lacks files it upstream as a **new step available to every brand**, never
> as a theme-local override. `--font-*` and `--weight-*` are identity and are theme-owned.
> The line is: *stacks and weights express who you are; sizes express how big the system is.*

Mapping the handoff's authored sizes onto the DS scale (`--text-2xs` 9.5 · `xs` 11 ·
`sm` 12.5 · `base` 13 · `md` 15 · `lg` 17 · `xl` 22 · `2xl` 28 · `3xl` 40 · `4xl` 44 ·

### Five colour rules that fall out of the measurements

**Rule C-1 — `--ochre` is a fill, `--ochre-d` is text.**
PROJECT.md records the dark palette as "clean" because `#B0722A` measures 4.56:1 on
`#161616`. That is true **on the page only**. On a raised card (`#1E1E1D`) it is 4.20:1 and
on an inset panel (`#242423`) 3.91:1 — both fail AA. Since Work's project cards, the
case-study screenshots and the entire admin sit on raised surfaces, the "dark mode is
already clean" claim does not survive contact with elevation. **Therefore: all ochre *text*
uses `--ochre-d` in both modes. `--ochre` is reserved for filled surfaces and decorative
strokes.** This is a strictly stronger contract than DS-02/DS-03 as written, and it costs
nothing.

**Rule C-2 — filled-accent ink flips between the two ochres.**
- On `--ochre` `#B0722A`: charcoal `#161616` ink = **4.56 ✅**; cream `#F4F1EA` = **3.52 ❌**
- On light `--ochre-d` `#8C591F`: cream `#F4F1EA` = **5.22 ✅**; charcoal = 3.07 ❌
- On dark `--ochre-d` `#C6883A`: charcoal `#161616` = **6.02 ✅**

So `--ink-inverse` is `#161616` for `--ochre` fills in both modes, and the light-mode
`--ochre-d` fill is the one surface that needs cream ink. **The handoff is wrong here in
both themes**: it specifies the hued icon as `#B0722A` with a white `h` (3.97:1) and Work's
icon squares as `color: #FFF`. Corrected in §Ivory→Charcoal rule 2.

**Rule C-3 — `--wire` and `--rule` are different tokens with different jobs.**
The handoff gives one border colour per theme (`#D5CFC2` light / `#33332F` dark), both around
1.3–1.4:1. That is fine for a decorative hairline and **illegal as the sole boundary of an
interactive control** (WCAG 1.4.11 needs 3:1). The admin is nothing but interactive controls
in light mode. So charcoal declares both, and the rule is:

> If the border is the *only* thing telling you where a control starts, it is `--wire`.
> If a fill or a heading already does that job, it is `--rule`.

`--wire` values above clear 3:1 on all three surfaces of their mode.

**Rule C-4 — the light-mode muted fix is `#6A6659`, not `#6E6A5E`.**
PROJECT.md proposes "~`#6E6A5E`". Measured: `#6E6A5E` is 4.79:1 on the page ✅, 5.36:1 on
paper ✅, but **4.46:1 on an inset panel ❌**. Since admin table zebra, disabled fields and
the pending-changes dashboard all put muted text on the inset surface, the value must clear
AA on the *deepest* light surface. `#6A6659` measures 5.09 / 5.46 / **4.74** — passes
everywhere with headroom. PROJECT.md's tilde was doing real work; this is the resolved value.

**Rule C-5 — dark elevation is surface + hairline, never shadow.**
The DS's `--shadow-1/2/3` are black-alpha (`rgba(0,0,0,.05–.12)`) and are invisible on
`#161616`. `--shadow-*` is a **geometry accent**, which D-31 puts on the *theme* side of the
line, so this is a charcoal-owned fix, not a DS gap. Charcoal's dark block restates:

```
--shadow-1: none;
--shadow-2: 0 0 0 1px var(--rule);
--shadow-3: 0 0 0 1px var(--rule-strong), 0 16px 40px rgba(0,0,0,.55);
```

`--shadow-3` keeps a real drop shadow because modals and the Lightbox sit over a `--scrim`,
where a black shadow *does* read. Everything below overlay level expresses elevation as
`--cream-2` / `--cream-3` plus a hairline.

### The exhaustiveness invariant — the load-bearing rule

D-27's specificity arithmetic is correct: `:root[data-brand="charcoal"]` is (0,2,0) and
`:root[data-brand="charcoal"].dark` is (0,3,0), which outranks `:root.dark` (0,2,0)
unconditionally. **But arithmetic alone does not make the cascade safe.** RESEARCH.md
measured the actual failure:

> A charcoal token declared in the light block and **not restated** in the dark block ties
> `:root.dark` at (0,2,0), so the winner is decided by whichever stylesheet Astro emitted
> last. Measured across four deliberately-constructed import orders: with charcoal after
> tokens, the **light** value applies in dark mode; with charcoal before tokens, `:root.dark`
> wins and charcoal is lost entirely. Light mode never breaks, because (0,2,0) always beats
> `:root` (0,1,0) — which is exactly why this bug ships.

**Therefore, the invariant, stated as a testable rule:**

> **`:root[data-brand="charcoal"].dark` MUST declare every custom property that
> `:root[data-brand="charcoal"]` declares.** Same count, same names. No exceptions, including
> tokens whose value is identical in both modes and tokens that are pure aliases.

With the invariant held, every charcoal token resolves at (0,3,0) in dark mode and the
cascade is **order-independent by construction** — no dependence on `@layer` (deferred to
Phase 06.1 by D-28) and no dependence on the D-33 manifest's import order.

This is why `--weight-extrabold`, `--weight-black`, `--ink-inverse` and `--focus` appear in
*both* tables above even though their values do not change: retiring or aliasing by omission
is precisely the failure the invariant catches.

Enforced by `.playground/check-theme-exhaustive.mjs` this phase, and handed to Phase 1 as a
`tokens.test.ts` case (it mirrors the DS's existing *"declares a light value for every token
the dark theme overrides"* assertion, ~15 lines against the existing `block()` /
`declaredIn()` helpers).

### Token-ownership allowlist (D-31, written as an allowlist so it cannot erode)

| Charcoal **MAY** redefine | Charcoal **MUST NOT** redefine |
|---|---|
| `--ink*`, `--cream*`, `--paper*`, `--panel*`, `--page-bg`, `--bg`, `--pg` | `--space-*` |
| `--rule*`, `--wire`, `--track`, `--fill-*`, `--scrim*`, `--g-bg`, `--g-bd` | `--text-*` |
| `--ochre*` (the charcoal accent, replacing `--amber*`), `--blue`, `--purple`, `--green`, `--red` and their `-d` / `-l` / `-ink` / `-vivid` / `-bg` variants | `--lh-*`, `--ls-*` |
| `--ds-illust-*`, `--surf-*` | `--ds-sidebar-w`, `--ds-snackbar-offset` |
| `--font*`, `--display`, `--mono`, `--serif`, `--weight-*` | `--z-*`, `--dur-*`, `--ease-*` |
| `--radius-*`, `--shadow-*` (geometry accents) | any sizing or spacing scale |
| `--focus`, `--focus-ring*`, `--error-ring` (derived from accent) | — |

The one non-obvious line, stated out loud because D-31 asks for precision: **`--text-*` is
sizing (DS-owned); `--font-*` and `--weight-*` are identity (theme-owned).** Sizes express
how big the system is; stacks and weights express who you are. See the §Typography ruling
for the consequence (G-11).

## Density Contract

**What Phase 0 owes Phase 06.1.** D-32 says Phase 0's job is "only to prove the shape."
The shape it proved is that **DS-11 as currently written cannot deliver a compact admin.**

### The measured problem

Counted in `../design-system/src/primitives.css` at v1.11.4 during this session:

| Declaration | Uses `var(--space-*)` | Hardcoded px | Tokenised |
|-------------|----------------------:|-------------:|----------:|
| `padding` | 21 | 135 | **13.5%** |
| `gap` | 11 | 91 | **10.8%** |
| `height` / `min-height` | **0** | **95** | **0%** |

Plus: `Button`'s `padding: "7px 14px"` is an **inline style object** in
`src/inputs/Button/index.tsx`, so it beats every CSS rule at every specificity and is
unreachable by any cascade-based density axis whatsoever.

DS-11 says density works by *"redefining spacing tokens."* Redefining `--space-*` would
therefore change ~13% of the padding, ~11% of the gaps, and **none** of the control heights
in the design system. An admin rendered at `data-density="compact"` under that definition
would be visually indistinguishable from the default.

**Phase 06.1's scope must widen:** density needs a **control-geometry token layer** —
`--control-h`, `--control-h-sm`, `--control-px`, `--row-h`, `--field-gap` — introduced first
and adopted by the primitives, *then* varied by the density axis. Filed as **G-2**.

### What "compact" concretely means

Numbers, not a vibe. `comfortable` is the DS's current behaviour, measured.

| Property | `comfortable` (today) | `compact` (target) | Δ |
|----------|----------------------:|-------------------:|--:|
| Control height — TextInput, Select, Button md | **36px** (`.ds-atom-input`) | **30px** | −6 |
| Control height — Button sm | 28px | 24px | −4 |
| Control height — Button lg / primary actions | 44px (`--space-11`) | 36px | −8 |
| Control horizontal padding | 10px | 8px | −2 |
| Control font size | `--text-base` 13 | `--text-base` 13 | **0** |
| Field label → control gap | `--space-2` 8 | `--space-1` 4 | −4 |
| Field → field vertical gap | `--space-4` 16 | `--space-3` 12 | −4 |
| Form group → group gap | `--space-6` 24 | `--space-4` 16 | −8 |
| Card / panel padding | 20px 22px | 12px 16px | −8 / −6 |
| Section break | `--space-8` 32 | `--space-6` 24 | −8 |
| **Table / DataGrid row height** | **44px** | **32px** | **−12** |
| Table cell horizontal padding | 16px | 12px | −4 |
| Table header height | 40px | 30px | −10 |
| DataGrid bulkbar padding | 8px 16px | 6px 12px | −2 / −4 |
| DataGrid footer padding | 10px 16px | 6px 12px | −4 / −4 |
| Sidebar width (`--ds-sidebar-w`) | 240px | 208px | −32 |
| Sidebar nav item height | 36px | 30px | −6 |
| Icon button hit area | 36px | 30px | −6 |
| Border radius | unchanged (`--radius-md` 8px) | unchanged | 0 |
| Font sizes | unchanged | **unchanged** | 0 |

**Two invariants that bound the axis.** Both are derived, and both must be written into
DS-11's acceptance criteria:

1. **Density never changes type size.** Only spacing and control geometry. A compact admin
   that also shrinks text is just a smaller admin, and it silently breaks every contrast
   assumption made at a given size. This is what keeps `--text-*` DS-owned and orthogonal.
2. **`data-density="compact"` MUST NOT apply below the phone breakpoint.** A 30px control is
   below the 44px touch-target floor (§Spacing exception 1). D-09 makes the admin
   phone-capable for light edits, so the phone layout stays at `comfortable`. Concretely:
   the density attribute is set at the `<html>` level but the DS must gate its effect behind
   `@media (pointer: fine)`, or the consumer must set it responsively — **which of those two
   is Phase 06.1's call, and Phase 0 records the requirement, not the mechanism.**

### How Phase 0 proves it

Per RESEARCH.md OQ-5's recommendation, adopted: the playground carries a **local prototype**
of the density overrides in `src/styles/density-compact.css`, applied under
`[data-density="compact"]`, with a header comment naming **DS-11** as the owner and stating
that the file is deleted with the playground. This is not the workaround D-32 forbids — the
playground is throwaway by construction and has no path to production (no adapter, no CI).

Each override the prototype has to write **because a DS value is not tokenised** is one line
of evidence for G-2. The deliverable is the diff: *"compact required N declarations, of
which M could not be expressed as a `--space-*` change."*

## Review Convention — how ~35 artefacts stay reviewable

D-03 requires admin states **exhaustively**. D-13 adds a draft/ready/published axis. D-09
adds a second layout. Naively: 7 screens × 6 states × 2 layouts = 84, plus ~12 cross-cutting
surfaces × ~2 states × 2 layouts ≈ 24 → **~108 artefacts**. Unbuildable in one phase and
unreviewable if built.

**The reduction that keeps D-03's guarantee.** D-03's promise is *"nothing is left for Phase
7 to invent."* That promise is kept by an **explicit, complete coverage matrix** — not by
rendering every cell. Most states do not live at screen scope: `loading` is a shell + list
treatment (2), `conflict` is one dedicated screen (1), `success` is a publish outcome (2),
`error` is three genuinely different treatments (3), `dirty` is one badge pattern applied
everywhere (1). Only `empty` is genuinely per-screen (4–5).

This section specifies the machinery that makes that reduction **verifiable by inspection**.
Without it the reduction is just a smaller pile.

### Artefact classes and ID scheme

Every artefact carries a stable ID. Findings, review comments and the coverage table all
cite it, so a review comment survives the playground's deletion.

| Class | Prefix | Count | What it is |
|-------|--------|------:|-----------|
| Screen | `S-` | 7 | An admin route in its populated state, desktop |
| Empty | `E-` | 5 | A genuinely per-screen empty state |
| Treatment | `T-` | 8 | A reusable state pattern, sketched **once** on its most demanding host |
| Overlay | `O-` | 9 | A modal, sheet, dialog or strip |
| Phone | `P-` | 4 | The four capabilities D-09 permits on a phone |
| Refusal | `R-` | 2 | The two designed "open on desktop" states |
| Public | `X-` | ~5 | Work, Photos, case-study long, case-study short, contact sheet itself |

≈ **35 admin + ~5 public artefacts.**

Canonical IDs (these are the contract; the planner may add, may not silently rename):


### The contact sheet — `pages/index.astro`

One page, four parts, built from the **first** sketch onward, never retrofitted (Pitfall 5).

**Part 1 — Index.** Every artefact as a labelled link, grouped by class, each with **one line
stating what it proves.** Not what it shows — what it proves. "S-photos: 39 real photos in
`DataGrid` at compact density, proving row height is legible at 32px" is useful;
"S-photos: the photos screen" is not.

**Part 2 — Coverage table.** 7 screens × 6 states = **42 cells**, none blank. Each cell is
exactly one of:

| Value | Meaning | Must carry |
|-------|---------|-----------|
| `designed` | A sketch exists for this exact cell | a link to the artefact ID |
| `inherits: T-n` | Covered by a treatment sketched elsewhere | the treatment ID |
| `n/a: <reason>` | This cell cannot occur | a one-clause reason, e.g. `n/a: /admin/site has no async load` |

**A blank cell fails review.** That single rule is what converts D-03's "exhaustively" from
an aspiration into a checkable property.

**Part 3 — Phone coverage.** D-09 permits exactly four capabilities and requires two
refusals, so phone is a **6-row list**, not a 7× multiplier on the matrix. Each row states
the capability and links `P-*` or `R-*`.

**Part 4 — Measurement readout.** The four Wave-0 scripts' latest numbers, inline: island
chunk bytes, `<script>` count, manifest CSS bytes, exhaustiveness PASS/FAIL. This puts the
evidence on the same page as the design, so a reviewer never has to correlate two artefacts.

### Machine-generating the matrix

VALIDATION.md states coverage is machine-checkable while quality is not. That is only true if
each screen declares its own states. **Contract:** every admin sketch route exports

```astro
---
export const SCREEN = {
  id: "photos",                       // matches the S- suffix
  route: "/admin/photos",
  entity: "portfolio_images.json",
  layouts: ["desktop", "phone"],      // omit "phone" where D-09 refuses
};
export const STATES = [
  { state: "populated", coverage: "designed",       ref: "S-photos" },
  { state: "empty",     coverage: "designed",       ref: "E-photos" },
  { state: "loading",   coverage: "inherits",       ref: "T-loading-list" },
  { state: "error",     coverage: "inherits",       ref: "T-error-inline" },
  { state: "dirty",     coverage: "inherits",       ref: "T-dirty-badge" },
  { state: "conflict",  coverage: "inherits",       ref: "O-conflict-diff" },
  { state: "success",   coverage: "inherits",       ref: "T-success-published" },
];
const state = Astro.url.searchParams.get("state") ?? "populated";
---
```

The contact sheet imports every `STATES` array via `import.meta.glob`, renders the table, and
**fails the build** on any state in the canonical six that no screen accounts for. Adding a
state is one array entry, not a new file. Seven route files cover forty-two cells.

### The six review passes

A reviewer walks the contact sheet top to bottom in this order, with one question per pass.
Six focused passes beat one unbounded scroll.

| # | Pass | The question being answered |
|---|------|----------------------------|
| 1 | Coverage table | Is any cell blank, or any `n/a` reason unconvincing? |
| 2 | Screens, populated | Does each screen's IA match its entity, and is the field catalog complete? |
| 3 | Empty states | Does each say what is missing **and** what to do about it? |
| 4 | Treatments | Are three error treatments genuinely distinct, and is `dirty` legible in all three places D-13 requires (screen, sidebar badge, dashboard)? |
| 5 | Overlays | Does `O-conflict-diff` actually let you resolve one file without abandoning another? |
| 6 | Phone + refusals | Are the four capabilities complete, and do the two refusals read as honest rather than broken? |

### Viewport and mode contract

Non-negotiable, because a sketch in the wrong mode hides the exact defect it exists to find.

| Class | Mode | Density | Viewport |
|-------|------|---------|----------|
| `S- E- T- O-` (admin, desktop) | charcoal **LIGHT** (D-08) | `compact` | 1440 × 900 |
| `P- R-` (admin, phone) | charcoal **LIGHT** | **`comfortable`** (44px touch floor) | 390 × 844 |
| `X-` (public) | charcoal **DARK** | `comfortable` | 1440 × 900 + 390 × 844 |

**Sketching the admin in dark mode is an anti-pattern**, not a preference: the light palette
is where DS-02/DS-03's contrast failures live, and dark hides them.

## Copywriting Contract

### Voice — public (D-43)

> **Idea first, in plain language. Then one hard technical fact.**

Two lengths, because there are two slots and they are not the same:

| Slot | Where | Shape | Budget |
|------|-------|-------|--------|
| **One-liner** | Home Act-2 grid, 13px DM Sans, ~380px column | One sentence. Plain-language purpose, then one concrete detail. | **60–110 characters**, must fit **2 lines** |
| **Card description** | Work project card, 15px, ~600px card | Two sentences. Sentence 1 is the one-liner's idea; sentence 2 is the hard fact. | **120–200 characters**, must fit **3 lines** |

D-43's diagnosis, confirmed against the data: **hued** and **TimeShift** already use this
shape. **Momentum** ("Goal tracker with adaptive daily targets, streaks, milestones, badges,
home screen widgets, and cloud sync.") and the **Design System** ("80-component React library
with semantic tokens, dark mode, and live Storybook docs.") are plain feature lists and need
rewriting. **Cairn** already carries its refusal as its idea and needs the least work.

Five rules, each of which the current copy breaks somewhere:

1. **No feature lists.** A comma-separated run of six nouns is a changelog.
2. **The hard fact is a number, a constraint, or a named technique** — never an adjective.
   "CIELAB" and "runs entirely on Cloudflare's free tier" qualify; "modern" and "powerful"
   do not.
3. **No superlatives, no "beautiful", no "seamless".** The audience is engineers.
4. **Status carries currency, not prose.** D-45's `Live` / `Maintained` / `Archived` badge
   says whether it is alive; the sentence must not also say it, and must never carry a date.
5. **The design-system one-liner must close by pointing at the page the reader is on.** It is
   the only project whose outcome the reader is looking at while reading it (D-38).

### Voice — admin

Second person. Name the object. State the count. Say what happens next. No exclamation
marks. Never "Oops". Never a bare "Are you sure?".

### The `[NEEDS AKHIL]` length-realism rule (D-40)

D-40's whole purpose is that build phases work against **real text lengths**. A six-word stub
where a paragraph belongs defeats it. So:

> **A `[NEEDS AKHIL]` marker MUST be followed by placeholder prose at the length the finished
> section needs — a minimum of 40 words for any paragraph-scale gap.**

Four supporting rules:

1. **The marker is short; the prose is full length.** The visible marker names what is
   missing; the paragraph after it is written at finished length.
2. **Every guessed value is an `<angle-bracket>` slot.** `<n> applications`, `since <month>`,
   `<metric>`. A guess that looks like a fact is worse than a gap.
3. **Never state a motivation or an outcome as fact.** Code shows *what* was decided, rarely
   *why*, and never the *outcome*. In front of engineers, an invented decision is worse than
   an admitted gap.
4. **An HTML comment above the marker states what was searched and why it came up empty.**
   That comment is what makes the final-phase interview efficient.

Enforced by `.playground/check-copy-length.mjs` (VALIDATION.md, Wave 0): every
`[NEEDS AKHIL]` marker must be followed by ≥ 40 words.

### Nine things that are not straight swaps

**1 — Ochre as text inverts its role, not just its value.**
The Brevo metrics (`+15% CONVERSION`) and the italic cross-link ("see the photographs →") are
`#B0722A` on ivory: **3.52:1, already failing AA before the port.** On charcoal dark
`#B0722A` reaches 4.56:1 on the page but **4.20:1 on a card and 3.91:1 on a panel** — still
failing wherever it matters. Both must become `--ochre-d`. This is a **role change**
(`--ochre` → `--ochre-d`), not a value swap, and it silently regresses if someone maps
"accent → accent". See Rule C-1.

**2 — The hued icon's ink is wrong in both themes.**
The handoff specifies the hued square as `#B0722A` with a white italic `h`: **3.97:1, fails**.
On charcoal it must be `#161616` ink on `#B0722A` (**4.56:1**). Work's other icon squares
(`#3E5A48`, `#52585E`) keep white — 7.61:1 and 7.20:1 — so **the ink colour is per-icon, not
global.** The Home spec's `#EAE7E0` on `#B0722A` is worse still at 3.22:1.

**3 — Card boundaries invert which property carries them.**
On ivory, a card is *lighter* than the page (`#FFFEFB` over `#F4F1EB`) and its border
`#E6E0D2` is essentially decorative — the **fill** draws the boundary. On charcoal dark the
fill delta between `#1E1E1D` and `#161616` is ~1.08:1, so the **border** becomes the sole
boundary. Therefore Work's project cards take **`--wire` `#727268`** in dark, not `--rule`.

> **Rule: on dark, a card's boundary is carried by its border; on light, by its fill.**

Mapping `#E6E0D2 → --rule` mechanically produces cards that visually dissolve into the page.

**4 — Shadows do not port at all.**
`--shadow-1/2/3` are black-alpha and invisible on `#161616`. Charcoal's dark block restates
them as surface + hairline (see Rule C-5). This is theme-owned under D-31, so it is a
charcoal deliverable, **not** a `00-FINDINGS.md` entry — and it must be *restated*, not
omitted, or the exhaustiveness invariant fails.

**5 — Photographs need an edge they did not need on ivory.**
On a near-white field every photo has an implicit boundary. On `#161616`, dark-toned
photographs — and the gallery skews dark: architecture at night, `intothemist`, wildlife —
bleed into the page. Two consequences:
- Photo tiles take `box-shadow: inset 0 0 0 1px var(--rule)` in **dark only**, none in light.
- **The LQIP blur-up placeholder must be the charcoal page colour, not white.** Every one of
  the 39 photos carries a base64 placeholder in `urls.thumb`; a white-backed placeholder
  flashes hard on dark. This is a Phase 5 build note that originates here.

The `scale(1.03)` / 0.6s hover, 10px radius and `overflow: hidden` all port unchanged.

**6 — The active filter pill flips colour, because its meaning is "maximum contrast".**
On ivory the active pill is filled *dark* (`#26231E` bg, `#F4F1EB` text). Its semantic is not
"dark" — it is *"maximum contrast against the field"*. On charcoal dark that becomes filled
**light**: `#EAE7E0` background, `#161616` text. Mapping the literal colours produces an
active pill that is invisible against the page. Inactive pills keep an outline, but the
outline is **`--wire`**, not `--rule` — a filter pill is an interactive control and its border
is its only boundary (WCAG 1.4.11, Rule C-3).

*Note:* the accent-reserved list includes the active pill **in light mode only**. In dark it
is the ink ramp, per the flip above.

**7 — Newsreader → Playfair is not size-neutral.**
Playfair Display has a larger x-height and heavier stems than Newsreader at the same pixel
size. The 52px page headers — and especially the italic "Photographs" — will read
**heavier and larger** after the swap, on top of the G-11 snap to 44px. Sketch the header at
both 44px Playfair and 52px Playfair beside the 52px Newsreader reference and decide by eye.
**Do not blind-swap the family and keep the number.**

**8 — Measure length: 1280px is too wide for muted body on dark.**
Work and Photos are 1280px; Home is 1080px. The sub-paragraph is already capped at 480px and
stays. But the Brevo band's hairline rows span the full 1280px with a serif title left and a
mono metric right, and on a dark field that gap reads as two unrelated things rather than one
row. **Cap the Brevo band at 1080px to match Home**, keeping the page at 1280px for the card
grid and the masonry. Flag in review; this is a DSGN-03 decision, not a token change.

**9 — Work's structure changes independently of colour, and must not be conflated with it.**
Two locked decisions restructure the page while it is being recoloured:
- **D-44** replaces the ivory 2×2 card grid + "ALSO — ENGINEERING AT BREVO" tail with **two
  bands: employment first, then projects.** Brevo, PharmEasy and MAQ become a
  professional-experience band; the five own projects sit below.
- **D-45** adds `Live` / `Maintained` / `Archived` status badges and removes date reliance.
- **D-38** makes it **five** projects, not four, so the 2×2 grid is gone regardless.

Sketch the recolour and the restructure as **two separate artefacts** (`X-work-recolour`,
`X-work`). If a reviewer dislikes the result you need to know which change caused it — the
same attributability argument that split cascade layers out of Phase 1 (D-28).
