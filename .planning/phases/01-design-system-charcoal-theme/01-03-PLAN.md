```ts
const SRC = join(__dirname);
const tokensCss = readFileSync(join(SRC, "tokens.css"), "utf8");

/** Extract the declarations inside the first `{...}` block of a selector. */
function block(css: string, selector: string): string;   // indexOf(selector) → indexOf("{") → indexOf("\n}")
function declaredIn(css: string): Set<string>;           // /^\s*(--[a-z0-9-]+)\s*:/gim

const lightTokens = declaredIn(block(tokensCss, ":root {"));
const darkTokens  = declaredIn(block(tokensCss, ":root.dark,"));

function srgb(c: number): number;
function luminance(hex: string): number;
function contrast(a: string, b: string): number;
function resolve(css: string, selector: string, name: string): string;  // follows var() aliases
```

Existing `describe` groups, all of which must keep passing:
- `token layer` — 4 tests. The first, *"declares a light value for every token the dark theme
  overrides"*, is the **dark ⊆ light** direction and its comment records the real regression it
  caught (`--rule-strong` shipped dark-only). **It is not redundant with the mirror this plan
  adds and may not be replaced by it.** The second, *"defines every custom property referenced
  anywhere in src"*, walks every `.css`/`.ts`/`.tsx`/`.mdx` under `src/` and therefore already
  reads `src/themes/charcoal.css`; it strips each file's own declarations first, so charcoal's
  `var()` aliases satisfy it locally.
- `token contrast (WCAG)` — includes *"muted text steps clear AA (4.5:1) on every surface, in
  both themes"* and *"the focus indicator clears the 3:1 non-text contrast floor (WCAG 1.4.11)"*.
- `inset surface visibility` — `--track` / `--fill-disabled` assertions.

**`block()`'s known fragility, and why the parse floor exists.** It finds the closing brace with
`css.indexOf("\n}", open)` — a `}` at column 0. If a theme block is ever indented, or gains a
nested rule, the slice truncates, `declaredIn` returns nearly nothing, the set difference is
trivially empty, and **the mirror passes for the wrong reason.** Phase 0's version asserts a
floor for exactly this and its failure message says so in words.

  <name>Task 1: The charcoal exhaustiveness mirror and its parse floor</name>
  <files>../design-system/src/tokens.test.ts</files>
  <action>
Run the sibling protocol §1 gate; confirm `charcoal-theme`.

Read `src/themes/charcoal.css` alongside the existing `tokensCss`, and derive two sets with the
**existing** `block()` / `declaredIn()` helpers — the whole point of extending this file rather
than writing a new one is that one parser and one WCAG formula serve both themes, so a
disagreement between the default theme and charcoal is a real disagreement rather than a
formula difference.

```
charcoalLight = declaredIn(block(charcoalCss, ':root[data-brand="charcoal"] {'))
charcoalDark  = declaredIn(block(charcoalCss, ':root[data-brand="charcoal"].dark {'))
```

Add these to the `token layer` describe:

**(a) The mirror — light ⊆ dark.** Assert `[...charcoalLight].filter(t => !charcoalDark.has(t))`
is empty. Write the failure comment so the *mechanism* is in the file, not just the rule: a
charcoal token declared only in light resolves at (0,2,0) in dark mode, which **ties**
`:root.dark`'s (0,2,0); the tie is then decided by whichever stylesheet the bundler emitted
last, and the two possible orders produce **two different wrong answers** — charcoal's light
value applied in dark mode, or charcoal dropped entirely. Note that light mode never breaks,
because (0,2,0) beats `:root`'s (0,1,0) unconditionally, which is precisely why this class of
bug ships unnoticed.

**(b) The other direction — dark ⊆ light.** Assert the reverse difference is also empty. This is
the same shape as the existing `tokens.css` assertion and catches the same real regression
(`--rule-strong` shipped dark-only). Rule C-5's note is the reason it is not redundant here:
one-directional exhaustiveness would have satisfied charcoal's own invariant while violating the
design system's, because charcoal's dark block redefines `--shadow-*` and its light block must
restate them.

**(c) The parse floor.** Assert `charcoalLight.size >= 25` **and** `charcoalDark.size >= 25`.
Use 25 as the floor, not the actual count from 01-01: a floor tolerates the additive growth this
phase and Phase 06.1 will keep doing, while still being far above what a truncated parse
returns. The failure message must say, in words, *that is not a small theme, it is a truncated
parse — check for an indented closing brace or a nested rule in the charcoal block* — because
the number alone reads like a scope question rather than a parser bug.

**(d) Count parity.** Assert `charcoalLight.size === charcoalDark.size`. (a) and (b) together
already imply it for name sets, but a same-name-twice typo in one block would slip past both,
and this is one line.

**Run the negative control.** Delete one declaration from the charcoal **light** block, confirm
(a) or (b) goes red naming that exact token, restore it, confirm `shasum -a 256` of
`src/themes/charcoal.css` matches the pre-break value. Then separately indent the charcoal light
block's closing brace by one space, confirm **(c)** goes red rather than (a) silently passing,
restore, and confirm the SHA again. The second control is the one that matters — it proves the
floor is doing the job the floor exists for.

Commit as `test(tokens): assert the charcoal exhaustiveness invariant in both directions`.

Eight tokens × 3 surfaces × 2 modes = 48, plus the six directional `--ochre` assertions in the
next paragraph = **54**. Assert the count itself — build the cases as data and assert the case
array's length is 54 — so a token silently dropped from a tier list is a failure rather than a
smaller green run. This is the same shape as the parse floor and for the same reason.

Write the expected ratios from the contract's tables into the test as *documented* values in a
comment beside each tier, and record in the SUMMARY whether every measured ratio reproduces the
contract to two decimal places. The tightest measured values, which are the ones a regression
will hit first: **7.01** (dark `--ochre-d-strong` on panel), **4.86** (light `--ochre-d` on

**panel** — the surface a page-only measurement never sees.

**Then the directional Rule C-1 assertion, which is the half of criterion 3 that is easy to get
backwards.** `--ochre` `#B0722A` is a **fill**, not text. Assert that it **fails** the 4.5:1
text bar on two of three **dark** surfaces — 4.20 on paper, 3.91 on panel — while **passing** on
the dark page at 4.56. Assert it also fails on the light page at 3.52.

Say in the comment why a test asserts a failure: `--ochre` is reserved for filled surfaces and
decorative strokes, all ochre *text* uses `--ochre-d` or `--ochre-d-strong`, and if someone

and Rule C-2's ink flip goes with it. The assertion is what makes that a build failure instead
of a preference. Do **not** relax it to `toBeLessThanOrEqual` on a wider bound — the point is
that the specific value is pinned in both directions.
