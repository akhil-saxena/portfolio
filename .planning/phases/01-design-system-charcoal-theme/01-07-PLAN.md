export interface LightboxProps {
  open: boolean;
  onClose: () => void;
  items: LightboxItem[];
  activeIndex?: number;
  onIndexChange?: (index: number) => void;

**Existing behaviour that must not regress:**
- Controlled **or** uncontrolled: controlled only when the caller supplies **both** `activeIndex`
  and `onIndexChange`; otherwise the component owns `internalIndex`. The index is always clamped.
- `useFocusTrap(panel, open)` — Tab cycles inside, initial focus lands on the close button, focus
  restores to the opener on close.
- `useScrollLock(open)` — reference-counted so a nested `ConfirmDialog` releases correctly.
- `useDismiss(open, onClose)` — Escape. **This is a stack, not a listener.** Its docstring records
  that fifteen components each had their own `document` keydown handler and one Escape press closed
  every open layer; only the topmost layer now reacts. Do not add a second Escape path, and do not
  bypass `useDismiss` for the backdrop.
- A separate `document` keydown effect owns **only** ArrowLeft / ArrowRight, with `navigateTo`
  wrapped in `useCallback` and re-subscribed on `index` change. The inline comment explains why:
  as a plain function it was recreated every render while the effect's dependency list omitted it,
  so the listener closed over a stale `navigateTo`.
- The always-dark invariant (D-350): backdrop `rgba(0,0,0,.92)`, and **no `:root.dark` overrides**.
  Charcoal must not change the Lightbox's appearance, and 01-20's snapshot parity will hold it to
  that.
- `role="dialog"` + `aria-modal="true"` + `aria-label={`Image lightbox: ${current.alt}`}`, with a
  `biome-ignore` comment explaining why a native `<dialog>` is not used.

**Rendered structure:** a single `.ds-atom-lightbox-backdrop` div (the panel, `tabIndex={-1}`)
containing `IconButton.ds-atom-lightbox-close`, optional `.ds-atom-lightbox-prev`,
`img.ds-atom-lightbox-image`, optional `.ds-atom-lightbox-caption`, optional
`.ds-atom-lightbox-next`. **The backdrop and the panel are the same element** — that is the single
most important fact for the backdrop-click task.

**CSS:** `src/primitives.css` lines 1471–1541 hold the ten `.ds-atom-lightbox-*` rules.
`scripts/split-css.mjs` derives `dist/css/lightbox.css` from the `DS atom: Lightbox` banner
section, and `src/css-split.test.ts` asserts the round trip is byte-exact — so any CSS added here
must go **inside** that banner section, or `npm run css:check` fails.

  <name>Task 1: Backdrop-click close and srcset/sizes passthrough</name>
  <files>../design-system/src/overlays/Lightbox/index.tsx, ../design-system/src/overlays/Lightbox/Lightbox.test.tsx</files>
  <behavior>
    - A `pointerdown`+`click` on the backdrop element itself calls `onClose` exactly once
    - A click on `img.ds-atom-lightbox-image` does NOT call `onClose`
    - A click on `.ds-atom-lightbox-caption` does NOT call `onClose`
    - A click on the close / prev / next `IconButton`s does NOT reach the backdrop handler twice
    - A drag that starts on the image and releases over the backdrop does NOT call `onClose`
    - `items[i].srcSet` and `items[i].sizes`, when present, appear on the rendered `img`
    - An item with no `srcSet` renders an `img` with no `srcset` attribute at all, not an empty one
  </behavior>
  <action>
Run the sibling protocol §1 gate; confirm `charcoal-theme`.

**Backdrop close.** The backdrop and the panel are the same element, so the naive
`onClick={onClose}` on that div closes the Lightbox on **every** click inside it, including the
image. Gate on the event target being the backdrop itself — `e.target === e.currentTarget` — which
is the standard form and is the only one that is correct for a self-backdrop.

Handle the drag case explicitly, because it is the one users hit by accident and a target check
alone does not catch it: a pointer-down on the image that releases over the backdrop produces a
`click` whose target is the backdrop. Record the element that received `pointerdown` and require it
to be the backdrop **as well**. Two conditions, both required.

Do not route this through `useDismiss`. That hook owns the Escape **key** stack; adding a pointer
path would put a second kind of event into a structure built for one. Call `onClose` directly — the
consumer's `onClose` is the same function `useDismiss` would call, so nesting still unwinds
correctly.

Consider whether backdrop close should be suppressible. It should not be, in this plan: no finding
asks for it, `Lightbox` has no fail-closed use, and the analogous request on `Modal` is a
**separate** finding (F-15-2) owned by plan 01-16. Adding a `closable` prop here would pre-empt
that plan's API decision. Leave it always-on and say so in the docstring.

**srcset.** Add `srcSet?: string` and `sizes?: string` to `LightboxItem` and pass them to the `img`
as `srcSet` / `sizes`. Document on the prop that `srcset` without `sizes` makes the browser assume
`100vw`, which is the right default for a full-bleed lightbox and therefore why `sizes` is
optional rather than required.

Two things to get right. Pass `undefined` rather than an empty string when absent, so no
`srcset=""` attribute is emitted — an empty `srcset` is not the same as no `srcset`, and a
consumer's snapshot would show the difference. And keep `src` **required**: it is the fallback for
a browser that ignores `srcset` and it is what `alt` pairs with. Do not make it optional.

Write the tests first, as behaviour, then the implementation. The tests are the reason `pointerdown`
tracking exists — the drag case is not obvious from reading the component.

<task type="auto" tdd="true">
  <name>Task 2: Swipe navigation and screen-reader slide announcements</name>
  <files>../design-system/src/overlays/Lightbox/index.tsx, ../design-system/src/overlays/Lightbox/Lightbox.test.tsx, ../design-system/src/primitives.css</files>
  <behavior>
    - A horizontal pointer drag of more than the threshold, leftward, advances to the next slide
    - The same drag rightward goes to the previous slide, with the existing wrap-around preserved
    - A drag shorter than the threshold does nothing — no navigation, and no `onIndexChange` call
    - A predominantly vertical drag does nothing, so a scroll gesture is not stolen
    - A swipe on a single-item Lightbox does nothing (`showNav` is false)
    - The live region exists in the DOM as soon as the Lightbox is open, before any navigation
    - Navigating updates the live region's text content to include the new one-based position, the total, and the new item's alt text
    - The live region text is empty on first open, so opening does not announce a slide change that did not happen
  </behavior>
  <action>
**Swipe.** Implement with pointer events on the backdrop element — `pointerdown` / `pointerup`
plus `setPointerCapture`, not a touch-event pair. Pointer events cover touch, pen and mouse-drag in
one code path; a touch-only implementation is inert to a pen, which is finding G-1's first recorded
defect in the legacy focal-point control and is worth not repeating. **Do not add a swipe library.**
`react-swipeable` was in the legacy portfolio's dependency tree; adding a package to read two
coordinates would be a new supply-chain surface for about fifteen lines.

The thresholds, and the reason each exists:
- **Horizontal distance** must exceed a minimum before it counts. Without it, every tap becomes a
  navigation, because a tap is a zero-length swipe.
- **Horizontal must dominate vertical** — compare absolute deltas. Without it a vertical scroll
  gesture that drifts sideways navigates, which feels broken and steals the gesture.

Pick concrete numbers, put them in named constants beside a comment saying what each rejects, and
state them in the SUMMARY so 01-20's human check can be phrased against them. Reuse the existing
`goPrev` / `goNext` so wrap-around, clamping and the controlled/uncontrolled split are inherited
rather than reimplemented — the `useCallback` comment in the file explains what goes wrong when
navigation is duplicated.

Guard on `showNav`: a one-item Lightbox must not respond, exactly as the arrow keys already do not.

If any CSS is needed — `touch-action: pan-y` on the backdrop so the browser does not claim the
horizontal gesture before the handler sees it — put it **inside** the `DS atom: Lightbox` banner
section of `src/primitives.css`. `scripts/split-css.mjs` slices on those banners and
`src/css-split.test.ts` asserts the split round-trips byte-exactly, so a rule outside the section
breaks `npm run css:check`.

**Announcements.** Render a visually hidden `role="status" aria-live="polite"` element inside the
panel, present **whenever the Lightbox is open** — not conditionally on having navigated. A live
region inserted at the moment its content changes is frequently not announced at all, because the
screen reader had nothing to observe; that is the standard failure and it is why the region must
exist first. Use the design system's existing visually-hidden utility rather than a local
`position: absolute` block; `src/primitives.css` already has one and `split-css.mjs` collects it
into `base.css` as something every consumer needs.

Choose `polite`, not `assertive`. dnd-kit's `assertive` regions are what G-13 measured, and two
assertive regions on one page with no way to share them is one of that finding's recorded
complaints. A slide change is not an interruption.

The announcement text must contain **the position and the total** as well as the item's identity —
G-13's central measured defect is speaking an identifier and **no position at all**, when position
is the one fact a navigating user needs. Use one-based numbering, and use `alt` as the identity
because it is already required and is already the human-readable name. Sketch:
`Image 2 of 36. Cliffs at dawn.`

Two edge cases to handle deliberately:
- **Empty on first open.** The region renders but says nothing until an actual navigation, so
  opening does not announce a change that did not occur. `aria-label` on the dialog already carries
  the initial item.
- **Do not announce a no-op.** A swipe below threshold, or an arrow key on a one-item Lightbox,
  must leave the region unchanged. Drive the text from the same `navigateTo` that performs the
  move, so a rejected gesture cannot reach it.

Add or extend a Lightbox story exercising a multi-item set with `srcSet` and a caption, so 01-20's
snapshot parity and 01-20's `test:a11y` run both cover the new markup. Keep it deterministic —
local SVG data URIs, not a remote image service. The visual suite's own docstring records that two
stories had to be converted from live picsum/pravatar fetches for exactly this reason.

Run `npm run test:a11y` for the Lightbox stories and confirm zero axe violations: a live region
with the wrong role, or a visually-hidden element that is actually `display: none`, both show up
there and neither shows up in a unit test.

Commit as `feat(lightbox): backdrop close, srcset, swipe and slide announcements`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| consumer-supplied `items` | `src`, `srcSet` and `alt` are consumer strings that reach `img` attributes. |
| pointer input → navigation | A new gesture path can steal scrolling or fire on an accidental drag, which is a usability failure that reads as a bug. |
| the assistive-technology surface | An announcement that never fires is indistinguishable from no announcement at all, and a test can pass on the markup while the speech is silent. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-01 | Tampering | `img srcSet` / `src` | accept | React escapes attribute values, and a `javascript:` URL in `src` does not execute on an `img`. `Lightbox`'s consumers are this project's own committed JSON, not user input. No sanitiser is added — one would be theatre here. |
| T-07-02 | Denial of service | scroll gesture | mitigate | Horizontal-dominance and minimum-distance thresholds, both as named constants with stated rejection cases; `touch-action: pan-y` so the browser keeps vertical scrolling. |
| T-07-03 | Spoofing | the live region | mitigate | The region is rendered from open rather than on change (a region inserted at change time is frequently never announced); text is empty until a real navigation; `polite` not `assertive`; `test:a11y` is run so a wrong role or a `display: none` hidden element is caught. |
| T-07-04 | Tampering | the `useDismiss` stack | mitigate | Backdrop close calls `onClose` directly and does **not** enter the Escape stack; no second Escape path is added. The hook's docstring records the one-press-closed-everything regression that structure exists to prevent. |
| T-07-05 | Tampering | `css:check` round trip | mitigate | Any new CSS goes inside the `DS atom: Lightbox` banner section; `npm run css:check` and `src/css-split.test.ts` both assert the byte-exact split. |
| T-07-SC | Tampering | npm/pip/cargo installs | mitigate | **No install.** Swipe is implemented with native pointer events; adding a swipe library for fifteen lines of arithmetic would be a new supply-chain surface for no gain. |
</threat_model>
