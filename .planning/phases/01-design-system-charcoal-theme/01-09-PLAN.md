<objective>
Close **E3, E4 and E5** — the three consumer-styling-boundary findings measured in a browser during
Phase 0. `Card` inlines `display: block` so a consumer's `display: flex` never applies; `Chip`
**clobbers** a consumer `className` where `Card` **concatenates**; and `Text` inlines its variant
colour so a page cannot recolour it without the `tone` prop.

Purpose: all three are the same bug in three places — **an inline style beating a class rule
without `!important`** — and all three were deliberately recorded as findings rather than worked
around, which is what makes them fixable now. This repository already has the right structure for
them: `src/styling-boundary.test.ts` exists as *"a ratchet, not an approval list"* for exactly this
class of defect, currently covering `transition` and `z-index`, with a docstring recording the
`Button` case where a reduced-motion guard *"looked correct in the stylesheet and did nothing in
the browser."* This plan adds `display` and `color` to that ratchet and fixes the three sites.

The measured consequence, so the value is not abstract: on `/work`, `.wk-card { display: flex;
flex-direction: column }` matches its element and `flex-direction` applies while `display` does
**not**, so `.wk-tags { margin-top: auto }` does nothing and the project cards do not bottom-align
their tech chips as designed.

Output: three small API corrections, two ratchet entries, and zero visual change to the default
theme.
</objective>

**`Card`** (`src/surfaces/Card/index.tsx`, 127 lines) — the pattern to keep, and the one line to
move:

```tsx
const baseStyle: CSSProperties = { display: "block", boxSizing: "border-box", fontFamily: "var(--font)" };
// …
className={`ds-atom-card${className ? ` ${className}` : ""}`}   // ← correct: concatenates
style={{ ...baseStyle, ...style }}                              // ← display: block wins over any class rule
```

`Card` already emits `data-variant`, `data-padding`, `data-radius`, `data-surface` and
`data-hover`, and `primitives.css` resolves them. So the class layer is already where the styling
lives; only these three properties are inline.

**`Chip`** (`src/inputs/Chip/index.tsx`, 87 lines) — the bug is the spread order:

```tsx
{ tone = "default", onRemove, icon, children, style, ...rest }   // ← className is NOT destructured
// …
className="ds-atom-chip"
style={{ ...baseStyle, ...toneStyles[tone], ...style }}
{...rest}                                                        // ← spreads className AFTER, replacing it
```

`className` falls into `...rest` and the rest-spread lands after the literal `className`, so a
consumer value **replaces** the atom hook. Measured: `chipClassAttr: "wk-chip"`,
`chipKeepsAtomClass: false`.

**The net visual change in the measured case was nil, and that was measured too** — `.dark
.ds-atom-chip`'s three declarations were already fully overridden by Chip's own inline
`baseStyle`/`toneStyles`, and its `[data-interactive]` focus rules do not apply to a
non-interactive chip. **The cost is latent, not current:** on an *interactive* chip the lost hook
takes the focus ring with it. Fix the API, and do not be misled into thinking there is a pixel to
find.

**`Text`** (`src/foundation/Text/index.tsx`) — already half-solved, and the existing comment says
what the intent was:

```tsx
// When token-size or tone is set, let CSS own those properties (don't emit
// inline overrides that would beat the data-attr rule).
const variantPick: CSSProperties = {
  ...(size ? null : { fontSize: variantBase.fontSize }),
  ...(tone ? null : { color: variantBase.color }),        // ← inlines colour whenever tone is absent
  ...
};
```

So the mechanism is understood and applied — but only for the *component's own* data-attr rules,
not for a consumer's stylesheet. With no `tone`, `color` is inlined and a page cannot recolour it.
`variantStyles` is `{ body: --ink-2, small: --ink-3, caption: --ink-3, legal: --ink-4 }`, and
`data-variant` is **already emitted on every render**, so the class layer can express all four
without any new attribute.

**`src/styling-boundary.test.ts`** (117 lines) — the ratchet to extend. It walks every
`index.tsx`, strips comments so prose about a property is not a match, and holds per-property
allowlists documented as *"a ratchet, not an approval list: it may shrink, never grow."* Follow that
convention exactly: any site this plan cannot fix goes in as an entry with a one-line reason, not as
a widened regex.

**`src/primitives.css`** — `scripts/split-css.mjs` slices it on `/* ─── DS atom: Name ─── */`
banners and `src/css-split.test.ts` asserts concatenating the slices reproduces the file byte for
byte. **Every rule added here must go inside the correct component's banner section**, or
`npm run css:check` fails. Note that `Card`, `Link`, `Heading`, `Divider` and `DatePicker` each own
**more than one** banner (a base section plus a later extensions section) which concatenate in
original order — so "the Card section" may be two places.

**Text.** Stop inlining the variant colour. `data-variant` is already emitted on every render, so
move all four variant colours into `primitives.css` as `.ds-atom-text[data-variant="body"] { color:
var(--ink-2) }` and the three siblings, inside the Text banner section. Then drop the
`...(tone ? null : { color: variantBase.color })` line from `variantPick`.

Get the precedence order right, because there are now four sources of colour and the existing
docstring already promises a specific ordering:

1. lowest — the variant's class rule (new);
2. the `tone` prop's `data-tone` rule (unchanged);
3. a consumer's class rule, by normal cascade;
4. highest — the deprecated `color` prop, which stays inline because it is documented as an
   override and removing that would be a second breaking change this plan has no mandate for.

The interesting case is 2-vs-3: a `data-tone` rule and a consumer class rule can tie on
specificity, and then source order decides — which is not a contract anyone should rely on. Resolve
it deliberately: keep the `data-tone` selector at a **higher** specificity than a bare class
(`.ds-atom-text[data-tone="…"]` is already (0,2,0) against a consumer's (0,1,0), so this holds
without doing anything) and **state it in the docstring**: passing `tone` means the component owns
the colour; omitting it hands the colour to the cascade. That is the sentence E5 is actually asking
for.

Leave `fontSize` exactly as it is. The `size`-vs-`variant` interaction is a different axis, it is
not in any finding, and touching it would move type metrics across 488 baselines.

**The ratchet.** Add `display` and `color` to `src/styling-boundary.test.ts` in the same shape as
