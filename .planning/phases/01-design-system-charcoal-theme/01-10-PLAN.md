<objective>
Close **E6**: adopt `--wire` on the controls it was declared for, and give `StatCard` the atom class
its siblings have.

Purpose: E6 is the most consequential rendering defect charcoal exposes, and it is a *design-system*
inconsistency rather than a theme problem. `.ds-atom-input` ships `background: var(--cream)`, and
charcoal's light `--cream` is `#F4F1EA` — **the page background**. Measured fill delta: **1.000:1,
exactly zero.** Its only boundary is `border: 1px solid var(--rule)`, and charcoal's light `--rule`
is `#D5CFC2` at **1.38:1**. So on charcoal light, a design-system text field has **no perceptible
boundary at all**, on the theme whose entire admin is interactive controls.

Charcoal already declares the right token. `--wire` is `#878173` light / `#727268` dark, measured at
3.44 / 3.72 on the page and **3.20 on the panel in both modes** — declared for exactly this job, at
exactly the WCAG SC 1.4.11 bar. Rule C-3 states the boundary in a form a reviewer can apply:

> **If the border is the only thing telling you where a control starts, it is `--wire`. If a fill or
> a heading already does that job, it is `--rule`.**

And Phase 0 measured that **no design-system control uses it**: `TextInput`, `Select`, `Card`,
`AlertBanner` and `Table` all bind `--rule`; only `Button variant="secondary"` binds `--wire`, and
it does so **inline**. The declarations are in stylesheets rather than inline, so CSS *can* reach
them — which is what makes this a fixable upstream inconsistency rather than an unreachable one.

Output: the control layer rebound, a computed-style gate holding it there, and one missing class
hook.
</objective>

**`Chip`** also declares `border: "1px solid var(--rule)"` in its inline `baseStyle` — read from
source at planning time. A non-interactive chip is a label and `--rule` is correct for it; an
interactive chip is a control. That distinction is the interesting case and task 1 has to rule on it.

**`src/tokens.test.ts` already has a `--focus` 3:1 gate** — *"the focus indicator clears the 3:1

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| control boundary → an accessibility criterion | SC 1.4.11 is a WCAG conformance requirement, not a preference. A control with a 1.38:1 sole boundary fails it outright. |
| a rebinding sweep → the whole library's appearance | Changing which token every field asks for touches nearly every control story's pixels. |
| `--wire` vs `--rule` | Two adjacent tokens whose difference is a rule rather than a value; the erosion mode is one component at a time. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-01 | Tampering | rendered control chrome | mitigate | Every `--rule` border is classified against Rule C-3 in a reviewable SUMMARY table before any edit; baseline diffs are reviewed individually, never blanket-updated, and the moved count is recorded so an unexpectedly small number is caught. |
| T-10-02 | Spoofing | the 3:1 gate | mitigate | Non-zero control count asserted; the second condition (perceptible fill delta **or** 3:1 border) closes the loophole where a transparent border on an identical fill would pass condition 1. |
| T-10-03 | Tampering | token erosion | mitigate | `--wire !== --rule` asserted in both themes and modes, so the two tokens cannot converge into one. |
| T-10-04 | Elevation of privilege | Phase 06.1's scope | mitigate | Only `Button`'s border colour moves out of inline; its `padding` — G-2's unreachable case — is explicitly out of bounds, as is anything in `F-15-7`'s control-geometry family. |
| T-10-05 | Denial of service | `StatCard`'s surface | mitigate | `glass` is retained because it is a shared class in the `ds-*` contract; the fix is additive, and removing it would silently drop the surface treatment. |
| T-10-SC | Tampering | npm/pip/cargo installs | mitigate | No install. |
