<objective>
Close the four field-contract findings: **E15** (`FieldProps` has no `required` flag), **E11**
(`FieldError` has no severity), **G-6** (`FormErrorSummary` entries cannot carry a link), and
**F-15-8** (`InlineEdit`'s accessible name is the fixed string *"Click to edit"*).

Purpose: all four are the same shape — a form primitive that is *nearly* complete, where the missing
piece forces every consumer screen to invent its own. E15's measured consequence is the clearest
statement of the cost: requiredness is encoded in the **label string** (`"Alt text (required)"`) and
repeated in the hint, *"which means every screen invents its own marker and they will not match."*
The native `required` attribute already passes through `TextInput`, so the **semantics are already
right; only the marker has no home.**

G-6 is the one with a measured build behind it. On both surfaces that need it — the D-18 publish
modal and the inline publish block — the three `Go to Résumé` / `Go to Photos` / `Go to Home` actions
had to render as **separate elements beside the summary**, in a second ordered list *"whose only
binding to the first is that the two arrays happen to be in the same order."* Reordering or
renumbering either array desynchronises them with nothing to catch it. The emitted markup is a
`<ul>` of plain text with no element in it that could take an anchor.

Output: four additive props, all backward-compatible, each with the distinguishing affordance rather
than only the data.
</objective>

**E15 — `required`.** Add `required?: boolean` to `FieldProps`. Render one marker, consistently, so
the finding's actual complaint — *"every screen invents its own marker and they will not match"* — is
answered by there being exactly one.

Three decisions to make deliberately and record:

1. **The marker's form.** An asterisk is conventional and terse. Whatever you choose, put it in a
   `primitives.css` rule inside the Field banner section keyed off a data attribute, not as a
   literal in the JSX, so a consumer can restyle it and a future locale can change it.
2. **It must not double-announce.** The `required` attribute on the control is already announced by
   assistive technology (it is what makes the semantics already correct). A visible asterisk that is
   *also* in the accessible name means "required" is spoken twice. Mark the visual marker
   `aria-hidden="true"`, and say why in a comment.
3. **The `group` interaction.** When `group` is true the wrapper is a `<fieldset>` with a
   `<legend>`; the marker belongs **inside the legend**. `group`'s own docstring explains that a
   `<label for>` may only point at a labelable element, and the same reasoning puts the marker with
   the grouping label.

`required` does **not** set the native attribute on the child — `Field` wraps arbitrary children and
does not own the control. Say that in the docstring: the prop is the *marker*, the native attribute
stays the consumer's job through the control's own `required`. Getting this wrong would make `Field`
appear to enforce validation it cannot see.

**E11 — `FieldError` severity.** Add `tone?: "error" | "warning"`, defaulting to `"error"` so every
existing call site is unchanged. Add the same to `Field`'s error slot so a warning can be expressed
through the scaffold, which is what UI-SPEC's *"`Field` + `FieldError` at warning severity"* asks
for.

Two things that are the substance of the fix rather than the plumbing:

- **The role must differ.** `role="alert"` interrupts. D-18's LENIENT warning must **not** interrupt
  while its STRICT publish block must. Use `role="alert"` for `error` and `role="status"` for
  `warning`. This is why the finding says the two *"render identically and both interrupt"* — the
  interruption is half the defect and a colour change would not fix it.
- **Not colour alone.** The treatments must differ by something a colour-blind or monochrome reader
  perceives — a word, an icon, or a border weight. G-7's evidence records the same principle for a
  neighbouring component in as many words: *"one of them is a colour and a colour alone is not a
  distinction."* Emit `data-tone` and let `primitives.css` carry both a colour and a non-colour
  difference.

Check the charcoal palette before choosing the warning colour: charcoal declares `--ochre*` and
inherits `--red`, `--blue`, `--green`, `--purple`. `--red` serves destructive in both modes and is
*"inherited, not redefined"* by charcoal. Do **not** invent a warning token — reuse an existing one
and verify its contrast with 01-02's `probeComputed` under charcoal light, which is the worst case.
If no existing token clears AA for warning text there, report it rather than adding an unmeasured
value; 01-03's contrast register is the gate that would otherwise be bypassed.

Extend `src/field-contract.test.tsx` with the cross-component assertion: every control that can
display a validation message routes it through `FieldError`, so severity is available everywhere at
once rather than per component. That is the assertion that keeps the twelve controls the docstring
mentions from drifting back apart.

**G-6 — the anchor.** Widen `errors` to
`Array<string | { message: string; href?: string }>` rather than replacing `string[]`. The finding's
proposed fix is `Array<{ message: string; href?: string }>`, but accepting the string form alongside
it costs one normaliser and keeps every existing call site compiling — and the finding itself notes
the component *"was not forked to add an href"*, so an additive widening is truest to how it was
recorded.

**The link must render on the list item, not beside it.** That is the entire finding: the
measured workaround produced *"a second ordered list whose only binding to the first is that the two
arrays happen to be in the same order"*, which desynchronises silently on a reorder. So the `<li>`'s
own content becomes the anchor when `href` is present. If it is absent, the `<li>` holds plain text.
Nothing renders outside the `<ul>`.

Three details worth getting right:

- **The anchor's accessible text is the message.** Not "Go to Résumé" beside "Résumé is missing a
  role" — the link text *is* the failure. That is what makes it deep-linking rather than a
  navigation aside, and it is why a generic "fix this" link would not close the finding.
- **Keep `role="alert"` on the container.** A summary appearing after a failed submit should
  interrupt; that is different from `FieldError`'s warning tone in task 1, and the asymmetry is
  deliberate. Note it in a comment so the two do not get "made consistent" later.
- **Replace the `biome-ignore` index key if you can.** With objects available, `href` (or
  `href ?? message`) is a stable key. If a duplicate is possible, keep the index key and keep the
  ignore comment — a wrong key is worse than an acknowledged one.

**F-15-8 — `InlineEdit`'s name.** Add an optional prop supplying the accessible name, defaulting to
the current `"Click to edit"` so nothing breaks. Check `src/interaction/InlineEdit/` and
`src/inputs/InlineEditField/` — both exist and may share the string; fix wherever it is hardcoded,
and if both, fix both with the same prop name.

Say in the docstring what the name should contain: **what is being edited**, so seven rows on one
screen announce seven different things. "Click to edit" describes the interaction, which the role
already conveys; the name should describe the target. That distinction is the finding.

**Do not touch `InlineEdit`'s 25px height.** That is F-15-7 / G-2 and belongs to Phase 06.1. Only
the accessible name changes here.

Run `npm run test:a11y` for the Field, FormValidation and InlineEdit stories. A required marker that

both cover the new markup.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| consumer-supplied `href` | An error-summary entry's `href` becomes an anchor target. A `javascript:` URL there is a real XSS vector, unlike an `img src`. |
| the assistive-technology surface | Four changes that all alter what is announced: a marker, two roles, an anchor's name and an accessible name. |
| existing call sites | Four widened prop shapes across a family the docstring says twelve controls depend on. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-01 | Elevation of privilege | `FormErrorSummary` `href` | mitigate | React does not block `javascript:` in `href` the way it does some attributes. Restrict rendered anchors to same-origin-shaped values — a leading `/`, `#`, or `.` — and render plain text for anything else rather than an anchor. Document that the prop is for in-app deep links, which is all D-18 needs. |
| T-11-02 | Spoofing | the required marker | mitigate | Marker is `aria-hidden="true"` so requiredness is announced once, by the native attribute; the docstring states the prop is the marker and not the semantics, so `Field` cannot appear to enforce validation it does not own. |
| T-11-03 | Spoofing | severity distinction | mitigate | `role="alert"` vs `role="status"` (interruption is half the defect), plus a non-colour difference; `test:a11y` run on the stories. |
| T-11-04 | Tampering | the charcoal palette | mitigate | The warning colour must be an **existing** token with its charcoal-light contrast verified via `probeComputed`; inventing an unmeasured value would bypass 01-03's contrast register, and is reported instead. |
| T-11-05 | Denial of service | existing consumers | mitigate | Every prop is additive with the previous behaviour as its default; `errors: string[]` still compiles and renders identically; `npm run typecheck` covers both `tsconfig.json` and `tsconfig.test.json`. |
| T-11-06 | Elevation of privilege | Phase 06.1's scope | mitigate | `InlineEdit`'s 25px height (F-15-7 / G-2) is explicitly out of bounds. |
| T-11-SC | Tampering | npm/pip/cargo installs | mitigate | No install. |
