duplicated: the bar's own `height` (or `min-height`) should read `var(--ds-appbar-h)`, so the property
and the paint cannot disagree.

Add a `min-height` rather than a fixed `height` if the bar can wrap — but note Phase 0 measured the
bar as **constant at all six viewport classes and not wrapping**, so a fixed height is defensible.
Record which you chose.

Document the property in the `AppBar` docstring with the consumer use case that produced the finding:
a full-viewport section under the bar needs `calc(100svh - <bar height>)`, and a bare `100svh` leaves
its bottom edge below the fold.

**E13's touch-target half.** `AppBar`'s brand link measured **20px** at 344px wide and its anchors
20px; `Footer`'s links measured **22.5px**. Raise both to 44px minimum at coarse pointers.

Do it with padding, not with `height`, and gate it on `@media (pointer: coarse)`:

- **Padding, not height**, because these are inline anchors: a `height` on an inline element does

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the shared type scale → both consumers | A step is public API the moment it ships; a renumbering breaks type everywhere silently. |
| a documented number → downstream copy | The portfolio's case-study copy quotes the component count. A wrong figure ships as a factual claim on a public page. |
| coarse vs fine pointer | A geometry fix applied to the wrong media context changes the desktop design. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-12-01 | Tampering | the type scale | mitigate | Additive only; a machine check asserts `--text-4xl`, `--text-5xl` and `--text-xl` still hold their exact values. 52px lands in `tokens.css`, not the theme, so 01-01's D-31 allowlist gate stays green. |
| T-12-02 | Repudiation | the component count | mitigate | Three sources reconciled to one asserted relationship, with the catalog's exclusions named and reasoned in a list the test reads — so an uncatalogued component fails CI by name rather than drifting. |
