<objective>
Close **E8 / G-13**: `Sortable` gains an accessibility passthrough so a consumer can replace what a
reorder announces.

Purpose: the gap statement here was **corrected by measurement**, and the correction is the finding —
transcribe the corrected form, because the original wording is wrong and a plan written against it
would build the wrong thing.

**The original wording** — *"passes no `announcements` / `screenReaderInstructions`, nothing is
announced"* — is false. dnd-kit's `DndContext` renders `<Accessibility>` with `defaultAnnouncements`
and `defaultScreenReaderInstructions` **when the consumer passes nothing**. Passing nothing gets the
defaults, not silence. Two live regions exist (`DndLiveRegion-0` and `DndLiveRegion-1`, one per
`DndContext`), and something **is** spoken.

**What is actually wrong is what it says.** Measured verbatim, by keyboard alone in Chromium 147
against the built `dist/`:

- `Space` → *"Draggable item abstract-intothemist was moved over droppable area abstract-intothemist."*
- `ArrowDown` → *"Draggable item abstract-intothemist was moved over droppable area abstract-lightscameraart."*
- drop → *"Draggable item abstract-intothemist was dropped over droppable area abstract-lightscameraart"*

Three defects in that text: it speaks **raw record ids**, never the photo's title; it speaks **no
position at all**, never *"position 2 of 36"*, which is the one fact a reorder user needs; and the
pick-up event announces the item as having moved **over itself**, which reads as a move that did not
happen.

So **the fix is to EXPOSE an announcer, not to pass one** — that is the finding's exact wording, and
it is the whole plan. `Sortable`'s prop surface is `{ items, onReorder, renderItem, id, className,
style }` with **no accessibility passthrough and no rest-spread onto `DndContext`**, so a consumer
has no replacement path at all.

One thing that is **not** broken and must not be touched: **the keyboard path itself works.** Every
reorder in the Phase 0 sketch was performed by keyboard alone. The movement is sound; only the speech
is not.

Output: two passthrough props on two components, defaults preserved, and a story that demonstrates a
useful announcement.
</objective>

```ts
export interface SortableItemData { id: string; [key: string]: unknown }

export interface SortableProps {
  items: SortableItemData[];
  onReorder: (items: SortableItemData[]) => void;
  renderItem: (item: SortableItemData, index: number) => ReactNode;
  id?: string;              // required when used inside SortableDndContext
  className?: string; style?: React.CSSProperties;
}

export interface SortableDndContextProps {
  children: ReactNode;
  onMove: (activeId, overId, activeListId, overListId) => void;
  renderOverlay?: (activeId: UniqueIdentifier) => ReactNode;
}
```

**Two places render a `DndContext`,** and both need the passthrough:
- `Sortable` renders its own `DndContext` **unless** it is inside a `SortableDndContext` — decided by
  the internal `SortableDndCtx` boolean context sentinel.
- `SortableDndContext` hosts the shared one for cross-list drag (D-12).

Both already build sensors the same way:
`useSensors(useSensor(PointerSensor), useSensor(KeyboardSensor, { coordinateGetter: sortableKeyboardCoordinates }))`.

**`SortableItemData` is `{ id: string; [key: string]: unknown }`** — an index signature. So a consumer
already puts a title on the item; the announcer just needs access to the items array and the ids,
which `Sortable` has and dnd-kit's announcement callbacks do not.

**dnd-kit's `Announcements` type** (`@dnd-kit/core@6.3.1`) is a record of callbacks —
`onDragStart`, `onDragOver`, `onDragEnd`, `onDragCancel` — each receiving an event with
`active` / `over` and returning a string or undefined. `ScreenReaderInstructions` is
`{ draggable: string }`. Re-export dnd-kit's own types rather than redeclaring them, so a dnd-kit
minor bump surfaces as a typecheck failure instead of a silent shape mismatch.

**Two related observations from the same measured run, recorded but not this plan's to fix:**
- A page with two `DndContext`s gets **two `aria-live="assertive"` regions with no way to share one.**
  That is a dnd-kit architectural property, not a `Sortable` prop gap. Record it; do not restructure
  dnd-kit's live regions.
- The live regions are **absent from the SSR'd HTML** because dnd-kit mounts them in an effect. That
  is the same family as E9's portal problem (plan 01-16) but it is dnd-kit's code, not this
  library's. Out of scope.

  <action>
Run the sibling protocol §1 gate; confirm `charcoal-theme`.

Add `announcements?: Announcements` and `screenReaderInstructions?: ScreenReaderInstructions` to
**both** `SortableProps` and `SortableDndContextProps`, importing both types from `@dnd-kit/core` and
re-exporting them from `src/index.ts` so a consumer can type its announcer without adding dnd-kit as
its own dependency. That re-export is what makes the passthrough usable rather than merely present.

**Pass through explicitly, not by rest-spread.** A `{...rest}` onto `DndContext` would let a consumer
set `sensors` or `collisionDetection` and silently break the keyboard path that Phase 0 measured as
working. Two named props, nothing else.

**Pass `undefined` when absent.** dnd-kit substitutes its defaults only when the prop is not set;
passing an empty object would replace the defaults with silence, which would make things *worse* than
the finding describes and would break the third behaviour in the list. That behaviour is the
regression guard.

**Handle the nested case honestly.** A `Sortable` inside a `SortableDndContext` renders no
`DndContext`, so its `announcements` prop has nowhere to go. Do not silently drop it. Either
(a) document on the prop that it is ignored when nested and the parent's is used, or (b) emit a
development-mode warning when both are set. **Prefer (a) plus a line in the component docstring** —
this library does not use dev warnings elsewhere, and introducing the pattern for one prop would be
inconsistent. Either way, the fifth behaviour asserts it.

Do not change the sensors, the `arrayMove` call, `verticalListSortingStrategy`, the
`useReducedMotion` handling or `SortableItem`'s transform logic. None of that is in the finding, and
the keyboard path working is the one thing the measurement confirmed is sound.
