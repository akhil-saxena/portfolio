<objective>
Close **E10 / G-3 / G-4** and the two `F-14-x` rows that belong with them: `toolbar={null}` does not
suppress the toolbar, marks cannot be restricted, a six-language syntax highlighter downloads to edit
a prose bullet, and there is no lossless output shape.

Purpose: this is the component behind the admin's résumé editor, and the finding here is **data loss**,
not a styling miss. Measured, at build time out of server-rendered HTML so the loss is a property of
the adapter rather than of a live session:

> Seven authored runs — plain, **bold**, plain, *italic*, plain, **bold**, plain — become **five
> segments**, because the italic run comes back as plain text and the two neighbouring plain runs
> **merge around it**. *"The stored value carries no record that a mark was ever there … nothing at any
> layer can detect it after the fact."*

And the marks that produce that loss cannot be turned off. With `toolbar={null}`: **⌘I still applies
italic** (`<em>` present), **⌘U still applies underline** (`<u>`), **⌘⇧H produces `<mark>`**,
**⌘⌥2 produces `<h2>`**. ⌘K is the one correction to the original wording — it was **never a keyboard
binding**, it is a toolbar button the component nevertheless advertises in its own hint list — but the
link mark is still reachable **without any keystroke**, because `autolink` is hardcoded on and typing
a URL creates one.

Underneath all of it is a shipped bug: `RichText` renders `!readOnly && (toolbar ?? defaultToolbar)`,
and `??` falls through on `null` — so **the exact value the prop's own docstring prescribes for
suppression selects the DEFAULT toolbar**, and twelve buttons render.

**The fix therefore needs two parts**, and the finding says so explicitly: `toolbar` must honour
`null`, **and** `marks` must configure the *extensions* rather than the toolbar — *"because suppressing
the toolbar was never what made the marks unreachable."*

Output: one bug fixed, one prop that actually restricts, one dependency made opt-in, and one output
decision made rather than inherited.
</objective>

**The shipped bug**, `dist/index.js:9143`:

```
!readOnly && (toolbar ?? defaultToolbar)
```

`??` falls through only on `null`/`undefined`, so `toolbar={null}` selects `defaultToolbar`. The
component's own docstring prescribes `null` for suppression.

**Always-registered extensions** (from `package.json` dependencies and the measured behaviour):
`StarterKit`, `@tiptap/extension-link` (with `autolink` hardcoded on),
`@tiptap/extension-underline`, `@tiptap/extension-highlight`,
`@tiptap/extension-code-block-lowlight` + `lowlight`, `@tiptap/extension-placeholder`.

**Measured reachability with `toolbar={null}`:**

| Input | Result | Note |
|---|---|---|
| `⌘B` | `<strong>` | the **one** mark the D-20 segment shape can carry — control case |
| `⌘I` | `<em>` | still applies |
| `⌘U` | `<u>` | still applies |
| `⌘K` | nothing | never a keyboard binding — the original gap wording was wrong |
| type a URL | `<a>` | `autolink` hardcoded on; **the link is reachable with no keystroke at all** |
| `⌘⇧H` | `<mark>` | Highlight registered unconditionally |
| `⌘⌥2` | `<h2>` | a node type, not a mark |

**F-14-2's cost:** `CodeBlockLowlight` is registered unconditionally and lazily downloads a
**six-language** grammar set — **12,718 B gzip** — to edit a résumé bullet.

**The G-15 connection:** `lowlight` and `highlight.js` are two of the five heavy families
`check-bundle.mjs` fails on, and `tsup.config.ts` already externalises the TipTap packages but **not**
`lowlight`. Making code blocks opt-in removes `lowlight` from the default module graph, which
strengthens 01-08's subpath result rather than duplicating it.

**`outputFormat` is `"html" | "json"` only.** `"html"` is **not an escape**: D-20 rules out a markup
string on principle, because if that string exists anywhere the stored-XSS class D-20 designs away is
back. The prototype asserted this by construction — `grep -q '"html"' RichTextBullets.tsx` exits 1.

**The D-20 segment shape** is `Array<{ text: string; emphasis?: boolean }>` — it carries **bold and
nothing else**, which is why restricting marks and fixing output are the same problem seen twice.

  <action>
Run the sibling protocol §1 gate; confirm `charcoal-theme`.

**Fix the `??` bug first**, on its own, because it is a one-character class of error and the rest of
the plan is easier to reason about once suppression works. Distinguish "not passed" from "explicitly
null": `toolbar === undefined ? defaultToolbar : toolbar`. Do **not** add a separate `showToolbar`
prop — the finding offers it as an alternative, but the docstring already prescribes `null` and
consumers have already written it, so honouring the documented contract is the smaller and truer fix.

**Then `marks`.** Add `marks?: Array<"bold" | "italic" | "underline" | "link" | "highlight" | "code">`
(match the actual registered set) and use it to **build the extension list**, not to filter toolbar
buttons. That distinction is the entire finding: *"suppressing the toolbar was never what made the
marks unreachable."*

Four specific things the extension configuration must get right, each mapping to a measured behaviour:

1. **`autolink` must go with the link mark.** It is hardcoded on, and it is the reason a link is
   reachable with **no keystroke at all** — the only mark with that property. Omitting `"link"` from
   `marks` must drop the Link extension entirely, autolink included.
2. **Highlight must not be unconditional.** `⌘⇧H` produced `<mark>` because the extension is always
   registered.
3. **Node types too, not only marks.** `⌘⌥2` produced an `<h2>`. StarterKit brings heading, list,
   blockquote and more. A `marks` prop that leaves headings reachable does not deliver the bold-only
   editor D-21 needs. Configure StarterKit's own options to disable the node types that are not
   wanted, and **name the prop honestly if it now governs more than marks** — if you widen it, say so
   in the docstring rather than letting `marks` quietly mean "marks and some nodes".
4. **When `marks` is absent, nothing changes.** Every existing consumer keeps every extension. The
   eighth behaviour is that regression guard.

Also make the toolbar consistent with the extension set: if a mark is not registered, its default
toolbar button must not render, or it renders a button that does nothing. That is toolbar filtering as
a **consequence** of extension configuration, which is the right direction — the finding's complaint
is about doing it the other way round.

Test by driving the actual key combinations, not by inspecting the extension array. Every one of the
seven measured rows in `<interfaces>` came from a real keypress in Chromium, and an assertion on the
configuration would pass even if TipTap ignored it.

**G-4 — the output shape.** The finding offers two routes: *"Add `outputFormat: "segments"`, or
document `"json"` + an adapter as the sanctioned path."* **Prefer the first.** The measured loss is a
property of the adapter, and an adapter documented as sanctioned is still an adapter that drops a
mark and merges its neighbours. A first-class `"segments"` output makes the shape the component's
responsibility, which is where D-20 wants it.

Whichever route, the **non-negotiable** part is the fourth behaviour: **a mark the shape cannot carry
must not vanish silently.** Seven runs in, five segments out, and *"nothing in the output naming which
one was lost."* Report it — a second return value, a callback, a thrown error in development. The
Phase 0 prototype proved the reporting is achievable: it surfaced *"1 thing(s) dropped on serialize —
Marks the shape cannot carry: italic. The editor still shows them. The stored value above does not."*
That is the bar.

Note the interaction with task 1 and state it in the docstring: with `marks={["bold"]}` there is
**nothing the shape cannot carry**, so the loss report should never fire. The two fixes compose — the
restriction prevents the loss, and the report catches the case where a consumer restricted less than
it serialises. Saying so is what stops a future reader treating one as redundant.

**Do not remove `outputFormat="html"`.** It is in use and removing it is a break no finding asked
for. Document in `README.md` why a new consumer should not choose it — if a markup string exists
