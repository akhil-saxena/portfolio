<objective>
Close **G-5** (`StatusPill`'s stages are job-domain-locked), **G-9** (`SegmentedControl` cannot serve a
crawlable category nav), **F-15-4** (`Badge` emits no class at all) and **F-15-5** (D-45's three
statuses are not distinguishable by fill on charcoal light).

Purpose: the first three are one story. `StatusPill`'s closed union is
`wishlist | applied | screening | interviewing | offer | closed`, so it *"appears on ZERO of the seven
admin screens"* and `Badge` stands in on **three distinct surfaces**, each for a different closed union
it cannot express. `CONTEXT.md` §Reusable Assets lists `StatusPill` as covering D-15; **it does not,
and that line is wrong.** Then `Badge`, the stand-in, *"emits no class at all and there is no
`badge.css`. One inline style object, hardcoded 9.5px type, on a component that appears on all seven
admin screens. A consumer cannot select, restyle or resize one."* And on charcoal light the resulting
pills are barely distinguishable: Live vs Maintained **1.02:1**, all three within **1.07–1.14:1** of the
page, so only the words separate them, at 9.5px.

**G-9 is a different animal and the finding is emphatic about why:** *"Not a hooks problem — an
ARIA-pattern problem."* `SegmentedControl` is a WAI-ARIA **radiogroup** with state-driven `onChange`
selection, so it has **no navigable anchor semantics at all**. PUB-04 needs prerendered
`/photos/[category]` routes with real links: crawlable, Back-button-capable, zero JS. An `as="nav"`
prop on one component **cannot serve both patterns cleanly** — the roles, the keyboard model and the
selected-state semantics all differ. The fix is a **small new sibling** sharing the CSS and nothing
else.

Output: one generalised component, one class hook, one legibility fix, one new component.
</objective>

**G-5 — generalise `StatusPill`.** Add a generic path — a `tone` plus a `label` — and keep the six job
stages as a **named preset** rather than deleting them, exactly as the finding specifies. `stage` and
the generic pair should be mutually exclusive at the type level (a discriminated union), so a call site
cannot supply both and leave the reader guessing which wins.

Reuse the tone vocabulary that already exists in this library rather than inventing a third one.
`src/foundation/tone.ts` carries `Tone` and `LegacyTone` and `Text` already consumes them
(`primary | secondary | muted | accent | danger | success` plus deprecated raw-token spellings). A pill
whose tones are named the same as `Text`'s is one vocabulary; a pill with its own names is a fourth
closed union, which is the shape of the defect being fixed.

**F-15-4 — give `Badge` a class.** Add `ds-atom-badge`, concatenating a consumer `className` using the
`Card`/`Chip` pattern 01-09 settled. Add a `DS atom: Badge` banner section to `primitives.css` and move
the inline declarations into it — this component *"appears on all seven admin screens"*, so it is the
highest-value class hook in the library. Replace the hardcoded `9.5px` with `var(--text-2xs)`, which is
the same value, so nothing moves visually while the size becomes reachable and overridable.

**F-15-5 — make three adjacent statuses legible.** This is the substance, not the plumbing. On charcoal
light the three D-45 fills sit within 1.07–1.14:1 of the page and Live vs Maintained is **1.02:1**, so
they are not distinguishable **as fills** and only the 9.5px words separate them.

Fix it with a **non-colour distinction plus a real fill difference**, not with three new hues:

- The tint tokens available under charcoal are `--ochre*`, `--blue`, `--green`, `--purple`, `--red` and
  their `-bg` / `-l` variants. Pick tones far enough apart that adjacent states clear a **1.2:1 fill
  delta** against each other and against the page, and verify with `probeComputed` under charcoal light
  — that is the failing case and the only one that matters here.
- **Add a non-colour signal too.** G-7's evidence states the principle for a neighbouring component in
  as many words: *"one of them is a colour and a colour alone is not a distinction."* A border weight,
  an outline versus a fill, or a leading dot — something a monochrome or colour-blind reader
  perceives.
- **Do not add a token.** If no existing combination clears 1.2:1 across three adjacent states, report
  it rather than inventing a value — 01-03's register is the gate and adding an unmeasured colour
  bypasses it.

Note what this plan does **not** do: it does not re-map D-13's or D-45's specific states to specific
tones. That mapping is UI-SPEC's and lives in the consumer. This plan makes a *distinguishable set*
available; choosing which state gets which tone is Phase 7's. Say so in the SUMMARY, so the finding is
not read as under-closed.

  <action>
Create `src/data-display/FilterNav/` as a **new sibling** of `SegmentedControl` — the finding is
explicit that this is *"not a hooks problem — an ARIA-pattern problem"*, and that an `as="nav"` prop on
the existing component *"cannot serve radiogroup and nav/link-list ARIA patterns cleanly."* Do not
touch `SegmentedControl`.

Props, minimal by design:

- `items: Array<{ href: string; label: ReactNode; id?: string }>`
- `activeHref` (or `activeId`) — which one gets `aria-current="page"`
- `ariaLabel` for the `<nav>` landmark — a nav without an accessible name is not usefully announced,
  and the same lesson was learned on `AppShell`'s banner slot in 01-13
- `className`, concatenated per 01-09's convention

Four hard requirements, each of which is the reason the component exists:

1. **Real anchors.** `<a href>`, not a button with a click handler. Crawlable and Back-button-capable
   both follow from this and neither can be added afterwards.
2. **Zero JS.** No state, no effects, no event handlers. Selection is a **prop**, derived from the URL
   by the consumer. If it hydrates, it is the wrong component — and Phase 5's `check-no-js` gate is
   the counterpart to G-15's bundle gate, so this will be measured.
3. **`aria-current="page"`, exactly one.** That is the nav pattern's selected-state semantics, and it
   is what differs from a radiogroup's `aria-checked`. Assert exactly one, since two is as wrong as
   zero.
4. **Share `SegmentedControl`'s CSS classes for visual parity.** The finding says *"shares
   `SegmentedControl`'s CSS classes for visual parity but renders real `<a href>` anchors"*. So reuse
   the existing class names where the visual is identical and add `ds-atom-filternav` only for what
   genuinely differs. Note the coupling in **both** components' docstrings — a future restyle of one
   must consider the other, and an undocumented shared class is how that breaks.

Register it in `src/index.ts` **and** `src/OverviewPage.tsx`. 01-12's count assertion will fail by name
if you skip the catalog — let that gate do its job rather than routing around it, and update the
README figure it checks against.

Add stories in both brands and a story showing it beside `SegmentedControl` for the parity check.
Run `npm run test:a11y`: a `nav` without an accessible name, two `aria-current` elements, or a link
with no discernible text all surface there.

Verify parity the honest way: capture both components in the same brand and mode and compare their
computed background, border, padding and font — via `probeComputed`, not by eye. "Looks the same" is
the requirement; a computed comparison is the only way to assert it.

Commit as `feat(filternav): add a crawlable anchor sibling to SegmentedControl`, and
`feat(statuspill): accept a generic tone and label` for task 1 if committing separately.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| consumer-supplied `href` | `FilterNav` renders anchors from consumer data. Same class as 01-11's `FormErrorSummary` href. |
| ARIA pattern boundary | Serving two patterns from one component is how both end up subtly wrong; keeping them separate is the mitigation, and shared CSS is the deliberate exception. |
| status colour → an accessibility claim | A three-state indicator distinguished only by a 1.02:1 fill is not a distinction, and it is currently shipping. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-18-01 | Elevation of privilege | `FilterNav` `href` | mitigate | Apply the same allow-shape rule 01-11 adopted for `FormErrorSummary` — render an anchor only for in-app-shaped values, plain text otherwise. `FilterNav` exists for prerendered in-app category routes, so nothing is lost. |
| T-18-02 | Spoofing | ARIA semantics | mitigate | A grep asserts no `role="radio*"`, no `useState`/`useEffect` and no `onChange` in `FilterNav`; exactly one `aria-current="page"` is asserted; `test:a11y` covers the landmark name. |
| T-18-03 | Spoofing | visual parity | mitigate | Verified by comparing computed background, border, padding and font between the two components in the same brand and mode — not by eye. |
| T-18-04 | Tampering | the shared CSS classes | mitigate | The coupling is documented in **both** components' docstrings, so a restyle of one cannot silently break the other. |
| T-18-05 | Spoofing | status distinguishability | mitigate | A 1.2:1 minimum fill delta between adjacent states and against the page, measured under charcoal light via `probeComputed`, **plus** a non-colour signal; no new token may be invented — an unachievable set is reported instead. |
| T-18-06 | Repudiation | the component count | mitigate | 01-12's assertion fails by name if `FilterNav` is exported without being catalogued; the gate is used rather than routed around. |
| T-18-SC | Tampering | npm/pip/cargo installs | mitigate | No install. `FilterNav` is built from existing primitives and plain anchors. |
