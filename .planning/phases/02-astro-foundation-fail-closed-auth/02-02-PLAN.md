<objective>
Resolve the two longest-lead items in the entire project before any code exists: confirm
`akhilsaxena.com` is on Cloudflare-managed nameservers, and provision an R2 custom domain in
front of the `portfolio-photos` bucket that demonstrably caches.

Purpose: The roadmap puts FND-07 in Phase 2 **for lead time, not because it feels like cutover
work**. Two facts make this urgent rather than tidy:

1. Cloudflare's own migration guide states, verbatim, *"Unlike Pages, Workers does not support
   any domain whose nameservers are not managed by Cloudflare."* If `akhilsaxena.com` is not on
   Cloudflare nameservers, **the chosen platform cannot serve the apex domain at all** — and
   that invalidates the stack decision, not just a config file. Discovering it at cutover means
   redoing DNS, secrets and CI simultaneously under outage pressure.
2. Every one of the 39 photos in `data/portfolio_images.json` currently points at
   `pub-2d90aedeebcf4142afe524930c3b6471.r2.dev`, which Cloudflare documents as rate-limited,
   uncached and "for development purposes only" — no WAF, no caching, no Bot Management. That
   directly blocks the Lighthouse 95+ goal and makes Lighthouse scores non-reproducible under
   rate-limiting.

This plan provisions the custom domain and **measures** that it caches. It deliberately does
**not** rewrite the 39 manifest URLs — that is Phase 3's CONT-04 ("No `pub-*.r2.dev` URL remains
anywhere in the repository"), a data migration with its own verification. What this plan owes
Phase 3 is one thing: the canonical hostname, written down.

Output: `02-DNS-R2-PREREQS.md` — nameserver evidence, the provisioned hostname, and a
before/after `cf-cache-status` measurement.

This plan touches no application code and shares no files with any other plan in the phase. It
runs in wave 1 in parallel with the supply-chain gate (02-01) so the developer's dashboard work
starts at minute one instead of after hours of scaffolding.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet → R2 custom domain | Anonymous readers fetch image objects; the bucket is intentionally public-read for photos, so the boundary controls *what* is exposed, not *who* reads it |
| registrar → Cloudflare zone | Whoever controls the nameservers controls where `akhilsaxena.com` points, including the apex the Worker will serve |
| Cloudflare dashboard session → account resources | This plan's provisioning step is performed with full account authority |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-05 | Information Disclosure | R2 bucket exposed via a new public custom domain | mitigate | The custom domain is attached to `portfolio-photos`, whose entire contents are already public via `pub-*.r2.dev`; Task 3 asserts the object served matches the existing origin byte-for-byte by SHA-256, proving no additional bucket was exposed. Later phases that write non-public objects (the `temp/` staging prefix) must not use this bucket's public prefix — recorded as a Phase 4 constraint in the handoff section. |
| T-02-06 | Denial of Service | uncached `pub-*.r2.dev` origin | mitigate | This plan's whole purpose: r2.dev is rate-limited and has no WAF or Bot Management. Provisioning a proxied custom domain puts Cloudflare's cache and WAF in front of the 39 photos. Task 3 fails the plan unless `cf-cache-status: HIT` is observed, so an unproxied record cannot pass as done. |
| T-02-07 | Spoofing | apex domain served by a Worker on non-Cloudflare nameservers | mitigate | `dig NS` evidence is recorded and re-asserted in Task 3's automated verify. Workers refuses domains not on Cloudflare nameservers, so a passing verify is also proof the platform constraint is satisfiable. |
| T-02-08 | Tampering | stale cached bytes after a same-key re-upload | accept (this phase) | Deterministic R2 keys plus a newly-cached domain means re-uploading a photo under the same key serves stale bytes indefinitely. No photo is re-uploaded in Phase 2, so the risk is not live yet. Recorded in the checkpoint text and the handoff section as a Phase 4 obligation (content-hashed keys or purge-on-write). |
| T-02-SC | Tampering | npm/pip/cargo installs | mitigate | This plan installs nothing and runs no package manager. It deliberately avoids `npx wrangler` precisely so it cannot bypass the still-open supply-chain gate in 02-01. |
</threat_model>
