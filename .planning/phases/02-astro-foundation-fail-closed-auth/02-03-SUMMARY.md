## Findings

### 1. `validateSecrets: true` is NOT a standalone build gate — it needs an importer

**This is the finding the plan asked for, and the answer is not the expected one.**

`astro@7.2.2` runs secret validation inside the Vite plugin's **module-resolution handler** for the `astro:env/server` virtual module (`node_modules/astro/dist/env/vite-plugin-env.js:71-121`). If nothing in the build graph imports `astro:env/server`, that handler never runs and **no validation happens at all**.

Measured, with `dist/` and `.astro/` wiped before every case so a stale artifact could not confound the control:

| Case | Build result |
|---|---|
| No module imports `astro:env/server`, **both** secrets absent | **PASSES** — validation never ran |
| A module imports `astro:env/server`, both secrets absent | **FAILS**: `[EnvInvalidVariables] CF_ACCESS_TEAM_DOMAIN is missing / CF_ACCESS_AUD is missing` |

So the configuration half of FND-04 is correct and complete, and the gate fires exactly as required the moment an importer exists — but **Phase 2 wave 2 has no importer yet**, because `src/lib/access.ts` is plan 02-04's. Until 02-04 lands, `npm run build` succeeds with no Access secrets configured.

**Consequences for later plans:**
- **02-04** — the moment `src/lib/access.ts` imports `astro:env/server`, the gate becomes live. No config change needed.
- **02-06** — the missing-secret negative control must run *after* 02-04, and must clear **all three** sources (see finding 2), not just delete `.env`.
- **02-08** — do not assume `validateSecrets` alone protects CI. If a stronger guarantee is wanted independent of import graphs, that is an explicit gate script, which 02-06 owns.

### 2. Which env mechanism feeds build-time validation: **all three, independently**

The plan asked for a statement of the form "build-time secret validation reads X; runtime binding secrets read Y". Measured with an importer present and `dist`/`.astro` wiped per case:

| Source present | `astro:env` build-time validation |
|---|---|
| `.env` + `.dev.vars` | passes |
| `.env` only | passes |
| `.dev.vars` only | passes |
| neither file, `CF_ACCESS_*` exported in `process.env` | **passes** |
| neither file, nothing in `process.env` | **fails** |

**Build-time secret validation reads Vite's resolved env — satisfied by `.env`, by `.dev.vars` (the Cloudflare Vite plugin injects it), or by plain `process.env`. Runtime binding secrets read `.dev.vars` locally and `wrangler secret put` in production.**

The practical consequence for **02-08**: CI does **not** need to write a `.env` file. Exporting `CF_ACCESS_TEAM_DOMAIN` and `CF_ACCESS_AUD` as workflow env vars is sufficient. The build log names its source explicitly (`Using secrets defined in .dev.vars` / `... .env`), which is a cheap CI assertion.

### 3. Client JS *is* emitted — 191 KB, referenced by nothing

The plan's strict assertion ("no JavaScript at all was emitted into `dist/`") **fails**, and per its own instruction it is reported rather than softened.

`dist/client/_astro/client.CJ90BtjY.js` — 191,633 bytes of React + `react-dom/client`.

Isolated with two reversible experiments (both rolled back, tree verified clean):

| Experiment | Chunk emitted? |
|---|---|
| `react()` registered, **no** React component rendered anywhere | **yes** |
| `react()` removed from `integrations` entirely | **no** |

Cause is in astro core, not in this project's code: `getClientInput()` (`node_modules/astro/dist/core/build/static-build.js:286-292`) unconditionally adds every renderer's `clientEntrypoint` to the client build inputs, alongside the discovered hydrated/client-only components. Registering `@astrojs/react` is sufficient; zero islands is irrelevant.

**The substantive claim the assertion protects still holds.** The shipped HTML contains **zero `<script>` tags** and **zero references** to the chunk (`grep` count: 0 across both pages). No visitor ever fetches it. It is dead weight uploaded to Cloudflare Static Assets, not shipped JavaScript.

Not fixed here, deliberately: the only remedies are dropping `react()` (impossible — React SSR is the point) or a post-build prune, and prune/gate scripts belong to 02-06 by this plan's own staging rule. **Recommended for 02-06:** either accept it and document, or add a prune step to the deploy gate.

### 4. Build output is `dist/client/`, not `dist/` — and deploy follows a redirect

With an adapter attached, Astro splits output into `build.client` (`dist/client`) and `build.server` (`dist/server`). `dist/index.html` never existed at the path the plan's verify assumed.

More importantly, the build writes `.wrangler/deploy/config.json` pointing wrangler at an **adapter-generated** config. `assets.directory` in the hand-written `wrangler.jsonc` is therefore never consulted at deploy time. Proven with `wrangler deploy --dry-run`:

```
Using redirected Wrangler configuration.
 - Configuration being used: "dist/server/wrangler.json"
 - Original user's configuration: "wrangler.jsonc"
✨ Read 12 files from the assets directory .../dist/client
```

The generated config resolves `assets.directory` to `../client` and carries `run_worker_first`, the `custom_domain` route and the `PORTFOLIO_BUCKET` binding through intact. `dist/server/.dev.vars` (which the build does create) is confirmed **outside** the resolved assets directory, and `dist/client/.assetsignore` additionally excludes `wrangler.json` and `.dev.vars` — so there is no secret-leak path into the public asset bundle.

`./dist` was left as authored, per the plan and its verify. **02-09 should confirm the redirect file is present at deploy time**, since `.wrangler/` is gitignored — a deploy run without a preceding build in the same workspace would fall back to the root config and serve `dist/client/*` under `/client/*`.

### 5. `wrangler deploy` currently fails — transiently, and by design

`wrangler deploy --dry-run` on the current fully-static build errors:

```
✘ [ERROR] Cannot set run_worker_first without a Worker script.
```

A build with **no** `prerender = false` route emits no Worker entry, so the generated config has no `main`, and `run_worker_first` without `main` is a hard wrangler error.

Confirmed transient by planting one temporary on-demand endpoint: `main: entry.mjs` appeared, and the dry-run completed cleanly, reporting the R2 and ASSETS bindings and reading 12 assets. **02-04 resolves this** by adding `/admin` and the API routes. No action needed here; `run_worker_first` must stay (AUTH-03).
