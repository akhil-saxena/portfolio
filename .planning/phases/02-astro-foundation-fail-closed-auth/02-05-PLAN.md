<objective>
Build the test harness that Criterion 2 requires: one project that executes tests **inside real
workerd** with real bindings, and one that issues real HTTP requests against the built site served
by real workerd. Then prove the harness is genuinely what it claims by making the workerd
assertion fail when run outside workerd.

Purpose: Criterion 2 does not merely ask that unauthenticated requests be rejected — it asks that
this be *"proven by a test running against real workerd rather than a mock."* That sentence is
load-bearing because the failure mode it guards against is specific: a jsdom or Node test of
`requireAccess()` proves nothing about the runtime that ships, and a green mock-based suite is
exactly the kind of evidence that lets a fail-open auth path reach production. Phase 0 learned the
same lesson from the other direction — four negative controls passed for the wrong reason before
the discipline of proving a control *bites* caught them.

This plan builds only the harness. It asserts nothing about auth, because auth does not exist
yet — plan 02-07 writes the auth tests into this harness in the next wave. Splitting them means
that when 02-07's tests are red, the redness is unambiguously about auth and not about a
half-configured pool.

This plan runs in parallel with 02-04 and owns `package.json` for this wave. 02-04 explicitly does
not touch the manifest, so the two cannot collide.

Output: `npm test` runs two projects — `workers` (inside workerd) and `integration` (HTTP against
`astro preview`) — both green, both proven to be real.
</objective>

<interfaces>
Two module specifiers matter and they are not interchangeable:

- `cloudflare:workers` — what **application** code imports (`src/lib/r2.ts` uses it). Available
  inside workerd, therefore available inside the pool.
- `cloudflare:test` — what **pool test** code imports for `env`, `SELF` and `fetchMock`. This is
  the pool's own module and exists only under `@cloudflare/vitest-pool-workers`.

Verify both against the installed package's own types before relying on them; if the pool's API
has moved, follow the installed version rather than this note.

Globals that exist in `workerd` and do **not** exist in Node — these are the basis of the
negative control: `WebSocketPair`, `caches.default`, and `navigator.userAgent` equal to
`"Cloudflare-Workers"`. Any one of them distinguishes the runtimes; assert on at least two so a
single API change cannot silently turn the control into a no-op.
</interfaces>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| test suite → the claim "auth fails closed" | The test harness is the evidence-producing boundary; a harness that silently runs somewhere other than workerd produces confident, false evidence |
| test process → local network | The global setup spawns a real HTTP server on the developer's machine and in CI |
| test process → external network | JWKS verification in later plans could reach out to a real Access endpoint if configuration leaked into tests |
