<objective>
Make every request to `/admin`, `/api/*` and `/_actions/*` that lacks a valid Cloudflare Access JWT
be rejected — **including when the Access configuration is entirely absent** — and prove it with
tests running inside real `workerd` and over real HTTP against real `workerd`.

Purpose: this is the plan the phase exists for, and the roadmap's note says why it is here rather
than in Phase 7:

> The moment `/admin` exists as a route in a deployed Worker it is a live attack surface. This is
> the single most important sequencing call in the roadmap, and it mirrors the exact failure mode
> found in the legacy app, where auth was to be "tightened later" via a comment nobody acted on.

The legacy `src/lib/access.ts` is the porting reference and also the anti-pattern. Read it with
`git show legacy/nextjs-portfolio:src/lib/access.ts`. Its structure is right — `jose`,
`createRemoteJWKSet`, a module-level JWKS `Map`, the `Cf-Access-Jwt-Assertion` header, `issuer` and
`audience` both checked. Its ending is wrong: when `CF_ACCESS_TEAM_DOMAIN` or `CF_ACCESS_AUD` was
unset it fell back to checking for the mere *presence* of a `CF_Authorization` cookie, with a
comment conceding "Not a security boundary on its own." That fallback existed so enabling strict
mode "can never lock the live admin out before the env vars are configured" — a reasonable-sounding
sentence that means *missing configuration grants access*. AUTH-02 exists to delete it: **there is
no cookie-presence fallback and no path that degrades to permissive.**

The fail-closed guarantee is expressed in three places, none of which relies on a code reviewer
noticing something: `astro:env` declares both secrets non-optional with `validateSecrets: true` so
absent configuration is a build failure (already in place from 02-03, with a control in 02-06);
`verifyAccessJwt` has no branch that returns permission; and this plan's tests assert the deny
behaviour inside the runtime that actually ships.

Output: `requireAccess()`, a prefix middleware that cannot run at build time, three wired routes,
and a test suite that discriminates.
</objective>

Read §"Auth — `jose` v6" in full. Four points are constraints:
- `jose@^6`'s `.` export resolves to the Web Crypto build (`dist/webapi`) with no Node built-ins,
  which is why it works in `workerd`. The v5 → v6 upgrade is API-compatible for
  `createRemoteJWKSet` + `jwtVerify`.
- The JWKS URL is `https://<team-domain>/cdn-cgi/access/certs`. Validate both `aud` (the Access
  application's AUD tag) and `iss` (`https://<team-domain>`); `exp` is checked implicitly by
  `jwtVerify`.
- Read the **`Cf-Access-Jwt-Assertion` header, not the cookie.** Cloudflare, verbatim: *"We
  recommend validating the `Cf-Access-Jwt-Assertion` header instead of the `CF_Authorization`
  cookie, since the cookie is not guaranteed to be passed."*
- `createRemoteJWKSet` already handles fetch, in-memory cache and cooldown. Keep a module-level
  `Map` keyed by team domain so the set survives across requests within an isolate. Do **not** add a
  KV cache layer — it adds a failure mode to the auth path for no benefit.

And the middleware trap, from the same section: Astro middleware *"runs at build time for all
prerendered pages"*, so a naive `src/middleware.ts` that denies unauthenticated requests would
execute during `astro build` against the public pages. Gate on `context.isPrerendered` and a path
prefix.

<interfaces>
Module split, and the reason for it. Keeping the `astro:env` read out of the verification logic is
what makes the verification unit-testable inside the `workers` pool, where the virtual
`astro:env/server` module is not available.

`src/lib/verify-access-jwt.ts`
- `export async function verifyAccessJwt(input: { token: string | null | undefined; teamDomain: string; aud: string }): Promise<boolean>`
- Returns `false` if `token` is absent or empty, or if `teamDomain` or `aud` is empty — this is the
  runtime half of AUTH-02 and it must be a plain deny, not a throw the caller might swallow.
- Otherwise builds/reuses a `createRemoteJWKSet(new URL('https://' + teamDomain + '/cdn-cgi/access/certs'))`
  from a module-level `Map` keyed by `teamDomain`, and calls
  `jwtVerify(token, jwks, { issuer: 'https://' + teamDomain, audience: aud })`.
- Returns `true` only on successful verification. Any thrown error resolves to `false`.
- Contains no branch that returns `true` without a completed `jwtVerify`.

`src/lib/access.ts`
- `export async function requireAccess(request: Request): Promise<Response | null>`
- Imports `CF_ACCESS_TEAM_DOMAIN` and `CF_ACCESS_AUD` from `astro:env/server`. Both are declared
  non-optional in `astro.config.mjs` with `validateSecrets: true`, so there is nothing to check
  for absence — absence is already a build failure. Do not add a runtime absence check that
  branches; if you want defence in depth, the only acceptable shape is one that denies.
- Reads the `Cf-Access-Jwt-Assertion` header. Does not read the `CF_Authorization` cookie at all.
- Returns `null` to allow, or a `401` `Response` with a JSON `{"error":"Unauthorized"}` body to
  deny. The 401 status matches the legacy error-code convention this project keeps
  (401 unauthorized, 400 malformed input, 409 conflict, 502 upstream, 504 timeout).
- The 401 body must not include the team domain, the AUD tag, the token, or any verification
  detail.

`src/middleware.ts`
- Exports `onRequest` from `astro:middleware`.
- Does nothing and calls `next()` immediately when `context.isPrerendered` is true. This is the
  build-time trap guard and it must be the first thing the function does.
- Otherwise, if `context.url.pathname` equals `/admin` or starts with `/admin/`, `/api/` or
  `/_actions/`, awaits `requireAccess(context.request)` and returns the 401 response if one came
  back. The prefix list must match `wrangler.jsonc`'s `assets.run_worker_first` exactly —
  `["/admin","/admin/*","/api/*","/_actions/*"]` — so the two halves of the defence cannot drift.
- Middleware is the blanket guard that covers routes nobody has written yet (the five D-05 admin
  sub-routes arrive in Phase 7). The per-route `requireAccess()` calls are defence in depth for the
  three routes that exist today, not a substitute.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet → `/admin`, `/api/*`, `/_actions/*` | Every request is untrusted; the `Cf-Access-Jwt-Assertion` header is attacker-controlled until verified against the JWKS |
| Worker → Cloudflare Access JWKS endpoint | An outbound dependency inside the auth path; its failure mode determines whether the system fails open or closed |
