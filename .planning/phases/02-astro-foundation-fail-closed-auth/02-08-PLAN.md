<objective>
Wire the pipeline Criterion 1 describes: *"A push to `main` deploys an Astro 7 + React 19 app to
Cloudflare Workers with Static Assets, **gated by CI** running lint, typecheck, build and tests."*

Purpose: the word "gated" is what shapes this plan, and it forces a documented deviation from the
research recommendation. `.planning/research/STACK.md` recommends **Workers Builds** — Cloudflare's
git integration and the Pages-equivalent CI/CD. But Workers Builds builds and deploys on its own
trigger, independently of GitHub Actions, and therefore **cannot be gated on a GitHub Actions
status**. A red test suite would not stop it. So this project deploys from a GitHub Actions job
that declares a dependency on the CI job, which is the only shape in which "gated by CI" is a true
statement rather than an aspiration. Record that deviation and its reason in the workflow file
itself, because the next person to read the research will otherwise "correct" it back.

Two secondary decisions this plan makes, both of which are security-shaped:

**CI never holds real secrets.** `astro:env` has `validateSecrets: true`, so the build requires
`CF_ACCESS_TEAM_DOMAIN` and `CF_ACCESS_AUD` to be *set* — but not to be *correct*, because Astro
reads server secrets at runtime from the Cloudflare environment rather than inlining them at build
time. So CI builds with the committed `.invalid` placeholders via `npm run bootstrap:local`, and
real values live only in `wrangler secret put`. Pull-request builds therefore have no secret in
scope at all, which removes an entire class of exposure from a public repository.

That reasoning has one dependency, and the plan verifies it rather than assuming it: **if Astro
were inlining secrets into the bundle, production would ship the `.invalid` placeholder.** CI
therefore greps the built output for the placeholder string and fails if it is present.

Output: two workflows — a CI gate that runs on every push and pull request, and a deploy that runs
only on a green CI for `main`.
</objective>

`.github/workflows/deploy.yml`
- Triggered by the CI workflow completing successfully on `main` — either `workflow_run` keyed on
  the CI workflow with a success conclusion and a `main` branch filter, or a single workflow
  containing both jobs with `needs: ci`. Either satisfies "gated by CI"; pick one, and state in a
  comment why the deploy cannot simply be Workers Builds.
- `permissions: contents: read`.
- `concurrency: { group: deploy-main, cancel-in-progress: false }` — deploys must queue, not
  cancel. Two pushes landing together must not race, and a cancelled deploy could leave the Worker
  and the assets out of step.
- Guarded so it runs only for `main` and only for a push-originated CI success.
- **Job-level `if: ${{ vars.DEPLOY_ENABLED == 'true' }}`**, with a comment explaining it. This
  workflow is committed one wave before the Cloudflare API token, the Access application and the
  Worker secrets exist, and `git.branching_strategy` is `none`, so it lands on `main` immediately.
  Without the guard, every push from that moment until plan 02-09 completes queues a deploy that
  fails on a missing token — polluting the `gh run list` history that 02-09 uses as its
  gate-ordering evidence — or, if the developer happens to create the token early, performs a real
  deploy before Cloudflare Access exists in front of `/admin`. A repository **variable** is used
  rather than a secret because the `vars` context is available in a job-level `if:` and the
  `secrets` context is not. Plan 02-09 sets `DEPLOY_ENABLED` to `true` as the last step of its
  credentials checkpoint, which makes enabling the deploy an explicit, dated act rather than a
  side effect of merging. A skipped job also records as skipped rather than failed, keeping the
  run history clean.
- Steps: checkout; setup-node from `.nvmrc`; `npm ci`; `npm run bootstrap:local`;
  `npm run deploy`, with `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` supplied from GitHub
  secrets as step-level `env:`.
- `npm run deploy` deliberately re-runs `gate:deps`, `build`, `test` and then `gate:routes` again
  inside the deploy job even though CI already ran build and test. That duplication is the point:
  the artifact that ships was produced in the same job that shipped it, the enforcing `gate:deps`
  runs on the ship path where it belongs, and the trailing `gate:routes` re-inspects the `dist/`
  that the test run's global setup last rebuilt rather than the one the in-build gate saw. Do not optimise it away by passing `dist/` between jobs as an artifact —
  `wrangler deploy` needs `node_modules` anyway to resolve
  `main: "@astrojs/cloudflare/entrypoints/server"`.

<verify_idiom>
**Every `<automated>` block below uses one idiom, and it is deliberately not the default.** The
Bash tool does not set `-e`, so a `;`-joined chain ending in `echo OK` reports success no matter
what failed inside it — the exit status is the `echo`'s. `set -e` is not the fix either: under it
a negative control written `grep BAD && { echo …; exit 1; }` aborts the shell in the *passing*
case, because the `&&` list returns non-zero when `grep` finds nothing.

The idiom used throughout, with no `set -e`:
- **Positive assertion** — `CMD || { echo "<what failed and why it matters>"; exit 1; }`
- **Negative assertion** — `if CMD; then echo "<what was found and why it is wrong>"; exit 1; fi`

No command appears bare. Every step either exits non-zero with a diagnostic or falls through with
status 0, so the trailing `echo` is a marker rather than the thing being reported. If you add a
step, write it in one of those two forms.
</verify_idiom>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → Cloudflare account | The deploy job holds an API token that can publish a Worker and read/write account resources |
| pull request (potentially from a fork) → CI runner | PR-triggered workflows execute repository-controlled scripts; any secret in scope is exposed to them |
| third-party action → runner | Every `uses:` executes someone else's code inside a job that may hold credentials |
| build environment → shipped bundle | If build-time env values are inlined, whatever CI supplied ships to production |
