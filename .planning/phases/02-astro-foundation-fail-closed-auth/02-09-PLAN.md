<objective>
Deploy the Worker for the first time and prove, against the live deployment, the two claims this
phase is built on: unauthenticated requests to `/admin`, `/api/*` and `/_actions/*` are refused
**even with the Cloudflare Access dashboard application switched off**, and the R2 binding resolves
in production.

Purpose: everything before this plan is evidence from a developer's machine. The roadmap's
criterion is about a **deployed** Worker, and the legacy app's failure was specifically a gap
between the dashboard's edge protection and the code behind it — its own `access.ts` comment said
the in-code gate existed *"so the write endpoints aren't a single dashboard toggle away from being
open,"* and then added a fallback that made them exactly that. The single most valuable check in
this plan is therefore the one that turns the dashboard toggle **off** and confirms the Worker still
returns 401 on its own.

Scope boundary, stated so nobody exceeds it: this plan attaches a Worker Custom Domain on a
**non-apex subdomain** of `akhilsaxena.com`. It does **not** attach the apex. `akhilsaxena.com` is
still pointed at the legacy Pages project, the live site being down is an accepted cost of the
rebuild, and moving the apex is cutover work with its own DNS-propagation window. Attaching it here
would trade a controlled outage for an uncontrolled one, and would gain nothing — a subdomain in the
same zone is enough to make Cloudflare Access, and therefore the entire auth path, testable end to
end. (Cloudflare Access applications are scoped to hostnames in a zone you control, which is why
validating on `*.workers.dev` alone cannot exercise Access at all.)

Output: `02-DEPLOY-VERIFICATION.md` — the production evidence for Criteria 1, 2 and 4.
</objective>
