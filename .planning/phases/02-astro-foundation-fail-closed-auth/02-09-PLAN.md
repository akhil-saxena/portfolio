<objective>
Deploy the Worker for the first time, prove the deploy was gated by CI rather than merely
configured to be, and probe the live deployment for the public route and the three protected
prefixes.

Purpose: everything before this plan is evidence from a developer's machine. The roadmap's
criteria are about a **deployed** Worker. This plan produces that deployment and the edge-layer
evidence for Criterion 1.

**What this plan deliberately does not do.** The probes here run with the Cloudflare Access
application live, so every refusal comes from Cloudflare intercepting at the edge *before the
Worker runs*. That proves the dashboard is configured. It proves nothing about the Worker's own
code — which is exactly the gap the legacy app fell into, its `access.ts` claiming the in-code gate
existed *"so the write endpoints aren't a single dashboard toggle away from being open"* while
shipping a fallback that made them precisely that. Plan **02-10** turns the toggle off and probes
the code behind it. Do not let the 302s recorded here stand in for 401s; 02-10 owns that section of
the evidence document and this plan leaves it as an empty heading on purpose.

Scope boundary: the Worker is attached to the **non-apex subdomain** recorded as
`WORKER_CUSTOM_DOMAIN` in `02-DNS-R2-PREREQS.md` and declared as a `custom_domain` route in
`wrangler.jsonc` by plan 02-03. `wrangler deploy` attaches it; no dashboard step and no redeploy is
needed. The apex `akhilsaxena.com` stays pointed at the legacy Pages project — moving it is cutover
work with a DNS-propagation window, and doing it here would trade a controlled outage for an
uncontrolled one for no gain.

Output: `02-DEPLOY-VERIFICATION.md` with the deploy evidence and the edge-layer probes.
</objective>

<verify_idiom>
**Every `<automated>` block below uses one idiom, and it is deliberately not the default.** The
Bash tool does not set `-e`, so a `;`-joined chain ending in `echo OK` reports success no matter
what failed inside it — the exit status is the `echo`'s. `set -e` is not the fix either: under it
a negative control written `grep BAD && { echo …; exit 1; }` aborts the shell in the *passing*
case, because the `&&` list returns non-zero when `grep` finds nothing.

The idiom used throughout, with no `set -e`:
- **Positive assertion** — `CMD || { echo "<what failed and why it matters>"; exit 1; }`
- **Negative assertion** — `if CMD; then echo "<what was found and why it is wrong>"; exit 1; fi`

No command appears bare. Every step either exits non-zero with a diagnostic or falls through with
status 0, so the trailing `echo` is a marker rather than the thing being reported. If you add a
step, write it in one of those two forms.
</verify_idiom>

   copy the **team domain** (`<team>.cloudflareaccess.com`) and the application's **AUD tag**.

4. **Worker secrets.** Run `npx wrangler secret put CF_ACCESS_TEAM_DOMAIN` and
