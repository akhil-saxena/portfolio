<objective>
Prove the deployed Worker refuses unauthenticated requests **by its own code**, with the Cloudflare
Access application switched off — and then prove the authenticated path works.

Purpose: this is the single highest-value check in Phase 2, and it exists because of a specific
sentence in the code this project is replacing. The legacy `src/lib/access.ts` said its in-code gate
existed *"so the write endpoints aren't a single dashboard toggle away from being open"* — and then
fell back to a cookie-presence check whenever `CF_ACCESS_TEAM_DOMAIN` or `CF_ACCESS_AUD` was unset,
which made them exactly that. Plan 02-09's probes ran with Access live, so every refusal came from
Cloudflare intercepting before the Worker ever ran. They cannot distinguish a correct implementation
from that legacy one.

This plan is separate from 02-09 for a structural reason, not a cosmetic one. A GSD checkpoint is
one pause and one resume and carries no `<automated>` block; folding "disable Access", "probe", and
"log in and confirm" into a single checkpoint would leave the phase's most important assertion with
no automated verification anywhere, and a collapsed handshake would let 02-09's edge-layer 302s be
recorded as if they were code-layer 401s. Splitting it into checkpoint → **auto with a real
verify** → checkpoint is what makes the 401 an asserted fact rather than a reported one.

It also carries the production half of FND-03: `/api/health` returning `"r2":"reachable"` to an
authenticated caller proves `env.PORTFOLIO_BUCKET` resolved from `cloudflare:workers` in the
deployed Worker, through a code path containing no absence-guard.

Output: the two sections plan 02-09 deliberately left as empty headings in
`02-DEPLOY-VERIFICATION.md`, filled with verbatim evidence.
</objective>

<verify_idiom>
**Every `<automated>` block below uses one idiom, and it is deliberately not the default.** The
Bash tool does not set `-e`, so a `;`-joined chain ending in `echo OK` reports success no matter
what failed inside it — the exit status is the `echo`'s. `set -e` is not the fix either: under it
a negative control written `grep BAD && { echo …; exit 1; }` aborts the shell in the *passing*
case, because the `&&` list returns non-zero when `grep` finds nothing.

The idiom used throughout, with no `set -e`:
- **Positive assertion** — `CMD || { echo "<what failed and why it matters>"; exit 1; }`
- **Negative assertion** — `if CMD; then echo "<what was found and why it is wrong>"; exit 1; fi`

No command appears bare. Every step either exits non-zero with a diagnostic or falls through with
status 0, so the trailing `echo` is a marker rather than the thing being reported. If you add a
step, write it in one of those two forms.
</verify_idiom>
