<objective>
Move all **156** remote photo URLs off `pub-2d90aedeebcf4142afe524930c3b6471.r2.dev` and onto
`https://images.akhilsaxena.com`, and make the old origin unable to come back.

Purpose: the `r2.dev` origin is documented by Cloudflare as *"for development purposes only"* —
no CDN cache, no WAF, rate-limited — and plan 02-02 **measured** that: `cf-cache-status` is not
merely `MISS`, it is **absent from the response entirely** on two consecutive requests, with no
`cache-control` and no `age`. Every one of the 39 gallery images therefore reaches the origin on
every request. Two consequences, and the second is why this is wave 1 of Phase 3 rather than a
Phase 5 performance pass:

- **Lighthouse 95+ on a 39-photo gallery is not reproducible against an uncached, rate-limited
  origin.** The number would move run to run for reasons that have nothing to do with the code.
- **This is a data migration of 156 values, not a config change.** Building the gallery's `srcset`
  against URLs that are about to change is rework, and rework in Phase 5 is rework against a
  Lighthouse budget.

Scale, re-measured this session rather than taken from the roadmap: the roadmap and the phase
prompt both say "four URLs per photo", which is right, but the phase-level figure that matters is
**156**, and `urls` has **five** keys — the fifth, `thumb`, is a base64 LQIP data URI carrying no
hostname and **must not be touched**. `02-DNS-R2-PREREQS.md` §"Scale of the Phase 3 rewrite this
unblocks" already records both figures; this plan confirms them before rewriting anything.

Output: 156 rewritten URLs, one canonical-origin module, one gate with a named exclusion set, and
a re-proof that the new hostname still returns `HIT` and still serves the same bytes.
</objective>

each with keys `id, title, category, tags, date, exif, urls, order, dimensions`. Every `urls`

Verified this session: **one** distinct remote host across all 156 values; **zero** anomalies in
the `-lg` / `-md` / `-sm` suffix convention; and every `original` pathname starts with
`/photos/<its own category>/`. So the rewrite is a pure host substitution with the pathname
preserved byte-for-byte, and any pathname change is a bug rather than a variation.

**The canonical target,** from `02-DNS-R2-PREREQS.md`: `https://images.akhilsaxena.com` (no
trailing slash). Two `A` records, both inside Cloudflare's published proxy ranges, `max-age=14400`.

**The `wrangler.jsonc` premise is probably wrong, and this plan should say so rather than obey it.**
That file's closing comment expects Phase 3 to add `R2_PUBLIC_URL` to `vars`, and
`astro.config.mjs`'s `env.schema` comment expects Phase 3 to extend the schema with it. Read both
comments — then check whether **anything in Phase 3 reads the value at runtime**. Nothing does: the
manifest holds absolute URLs, and the only writer of new URLs is the Phase 4 Actions pipeline,
which runs on a Node runner and not in the Worker. `astro.config.mjs`'s own comment states the rule
that settles it — *"declaring them now would force the developer to provision secrets that nothing
in Phase 2 reads"* — and `validateSecrets: true` means a declared, unprovisioned var fails the
build. So the origin belongs in a plain module this phase actually imports, and `wrangler.jsonc` /
`astro:env` gain it in **Phase 4**, when a consumer exists. Record the deferral in the summary so
