<objective>
Turn `site_config.categoryColumns` from a Title-cased string map into canonical category records
`{ id, label, columns }` (D-25), and decide what happens to its eighth key.

Purpose: ADR-002 deleted `/admin/site` and, in doing so, **made this phase's referential-integrity
rule load-bearing**. Its §4 is explicit: *"the schema module must assert every `photo.category`
exists in `site_config`'s ids, so a bad hand-edit fails the build rather than shipping quietly.
D-25's record shape stays correct — it kills the Title-case/lowercase drift… and a transform that
does not exist cannot disagree with the data."*

That rule is only as good as the id set it checks against, which is why the record migration has to
land before the schema (03-06) rather than beside it. Today the two files disagree about the
spelling of a category and nothing reconciles them except a render-time transform: the legacy
`PropertiesPanel` Title-cased on the fly with `c.charAt(0).toUpperCase() + c.slice(1)` to populate
its `<select>`. Making display and key different **fields** removes the transform entirely.

**Measured this session, and it makes the migration easier than the documents imply:**

- `data/portfolio_images.json` holds **seven** distinct categories, all lowercase: `abstract,
  architecture, nature, portraits, product, street, wildlife`.
- `data/site_config.json` holds **eight** keys: those seven Title-cased, plus `"All": 3`.
- `label === id[0].toUpperCase() + id.slice(1)` holds for **all seven**. So the label column carries
  no information today and the migration is lossless and mechanical. That is fine — the point of
  D-25 is not that the label differs *now*, it is that it *can*, without the id moving.
- Every one of the seven has at least one photo; the only key with no photo is `"All"`.

Output: seven category records, a decision on `"All"` and on the filter-row order, and a test
proving the retired map is fully recoverable from the new shape.
</objective>

  <decision>Is `"All"` a category record, and what order do the categories sit in? (OD-2)</decision>
  <context>
`categoryColumns` has eight keys and there are seven real categories. `"All": 3` is the column
count for the unfiltered gallery — a rendering property of a view, not a property of a category.

This matters beyond tidiness. The referential-integrity rule ADR-002 handed to this phase reads
*"every `photo.category` exists in `site_config`'s ids."* If `all` is an id, that rule accepts
`category: "all"` on a photo, which is the exact orphaning it exists to prevent — and the only fix
would be a hardcoded `"all"` exclusion inside the check, which is a second source of truth about
what a category is.

Separately: object key order is incidental, array order is a decision. Today the keys read
`All, Abstract, Architecture, Nature, Portraits, Street, Wildlife, Product` — alphabetical except
`Product`, which sits last. Once these become an array, that order becomes the filter row's order
and it is committed.
  </context>

**Write `scripts/migrate-site-config.mjs`** implementing the checkpoint verdict.

- `id` is the **lowercased** map key. `label` is the map key **verbatim**, not a re-derived
  Title-case — the whole point of D-25 is that label is authored data, and computing it here would
  reintroduce the transform in the migration instead of the renderer.
- `columns` is the map value unchanged.
- Order the array as decided at the checkpoint, and write the chosen ordering rule in a comment
  beside it so the next person does not re-sort it thinking the order was accidental.
- Idempotent: a second run reports 0 changes and leaves the file byte-identical.
- `JSON.stringify(data, null, 2)` plus a trailing newline. `data/` is Biome-excluded
  (`biome.json` → `"!data"`), so nothing will reformat it for you.

**Write `test/content/site-config-migration.unit.test.ts` — the losslessness proof.** It must
reconstruct the *old* map from the *new* records and compare it to the previous committed revision
(`git show HEAD~1:data/site_config.json`, falling back to `HEAD`):

- For each new record, `Title(record.id)` must be a key in the old map — this catches an id that
  was mangled on the way through.
- `record.columns` must equal the old map's value for that key — this catches a lost or transposed
  column count, which is the failure mode a diff of an 8-line file makes very easy to miss.
- Every old key must be accounted for exactly once, either as a record or as the explicitly-named
  `"All"` disposition decided at the checkpoint. **Not "the remaining key is ignored"** — the test
  names it, so a ninth key appearing later fails rather than being silently absorbed.
- Assert the record count (7 or 8, per the verdict) so a test iterating an empty array cannot pass.
- Assert every `photo.category` resolves in the new id set, and — the direction people forget — that
  every id has at least one photo. An id nothing references is how a category with no photos ships
  as an empty filter tab.

**One thing this test must not do:** derive its expected labels by Title-casing the ids. That would
make it green against a migration that dropped `label` entirely and let the schema default it,
which is the transform D-25 exists to delete, reintroduced inside its own regression test.

Commit: `content(site): make categories canonical records with separate id and label`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a hand-edited `site_config.json` → 39 photo records | ADR-002 removed the screen that guarded this file. A hand-edit is now the only way it changes, and there is no UI between the author and the damage. |
| category `id` → `photo.category` | The join key for the entire gallery. Renaming an id silently orphans every photo that used it — 14, in the worst case. |
| category `label` → the rendered filter row | The display string. Renaming it must be free of consequence, which is the whole reason it is a separate field. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-03-01 | Tampering | category ids | mitigate | Ids are lowercase and asserted so; the label is carried verbatim rather than re-derived, so no case transform exists between the two files that could disagree with either. |
| T-03-03-02 | Tampering | column counts | mitigate | Losslessness proof reconstructs the retired map from the records and compares to the previous git revision, with a transposition negative control. An 8-line diff is exactly the size at which a swap is invisible. |
