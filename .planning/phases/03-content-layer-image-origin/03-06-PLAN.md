<objective>
Write the one schema module, and make a second one impossible.

Purpose: criterion 1 is not *"validation exists"* — it is *"that same module is what the build, the
write path and the admin's form errors all consume; **validation cannot drift between them**."* The
roadmap says this explicitly and the phase prompt sharpens it: *three copies that agree today is a
failure, not a pass.* So the deliverable is two things — a module, and a structural argument that no
rival can exist.

The rule ADR-002 handed this phase is the sharp end of it. Deleting `/admin/site` was justified on
the grounds that *"a guard does not need a screen"* — the guard being **every `photo.category` must
exist in `site_config`'s ids**. There is now no UI between a hand-edit and 14 orphaned photographs;
this module is the only thing standing there. Two more cross-file rules found by probing the data
this session, neither of which any document names, are on the same footing: all six
`home_config.peekIds` are photo ids, and every `peekPositions` key is one of those six. `/admin/home`
edits both in Phase 7, and a peek id pointing at a deleted photo renders a silent blank tile.

**Two things this plan must not do, both of which are the easy version of the job:**

- **It must not restate the bullet grammar.** `containsHtmlTag` is imported from `src/lib/bullets.ts`
  (03-02). A regex in a zod refinement that *happens to agree* with the parser is the second
  definition this plan exists to prevent, written by the plan that exists to prevent it.
- **It must not install zod.** `astro@7.2.2` bundles `zod ^4.3.6` and re-exports it as `astro/zod`;
  the resolved copy is **4.4.3**. `research/STACK.md` records why a second copy is a hazard —
  *"type-identity mismatches with `defineCollection`"* — and 03-07's content collection depends on
  the schema object being the *same* zod's.

Output: five per-file schemas, one cross-file validator, and a gate proving nothing else validates
content anywhere in `src/`.
</objective>
