<objective>
Close the render half of criterion 3, and prove both halves with one test on one payload.

Purpose: criterion 3 reads *"A résumé bullet containing a script tag is stripped at both the write
boundary and the render boundary, verified by a test — the legacy stored-XSS class is closed
structurally, not by convention."* 03-02 made the stored shape unable to express a tag; 03-06 made
the schema reject one. Neither says anything about what a renderer does — and the legacy defect was
**entirely** a rendering defect: `Timeline.tsx:48` plus three admin components passed bullet strings
to `dangerouslySetInnerHTML`, with **no sanitiser anywhere in the repository**. A correct store with
a careless renderer reproduces the hole exactly.

**The interaction that makes this subtler than it looks.** Because the stored shape is bold-only
markdown, `<script>` cannot be *expressed* — so a test that stores a script tag and observes it not
rendering is testing a case the schema already refuses to admit, and would pass against a renderer
that is wide open. The honest way to interrogate the render boundary is to hand the renderer a run
whose `text` field carries the payload directly, bypassing the store. That is not contrived: it is
what any future code path constructing runs programmatically produces, and it is the only question
the schema has not already answered.

**Why one test and not two.** The criterion asks for *a* test covering both boundaries. Two tests
with two payloads can both pass while disagreeing about what "a script tag" is — one exercising
`<script>`, the other `<script >`, neither `<img src=x onerror=1>`. One payload crossing both
boundaries is a stronger claim and a shorter file.

Output: a renderer that emits elements and never strings, a gate banning the sinks that made the
legacy hole possible, and the test criterion 3 names.
</objective>

**`src/lib/bullets.ts`** (03-02) exports `parseBullet(s): BulletRun[]`, `serializeBullet`,
`containsHtmlTag`, and `type BulletRun = { text: string; bold: boolean }`.

**`src/schemas/resume.ts`** (03-06) rejects any bullet where `containsHtmlTag` is true, and any
bullet `parseBullet` throws on. That is the write boundary this plan's test also exercises.

**The render target.** `astro.config.mjs` carries `integrations: [react()]` with
`@astrojs/react@6.0.2` and React 19.2.8. `tsconfig.json` sets `jsx: "react-jsx"` and
`jsxImportSource: "react"`, so a `.tsx` component needs no React import.

**Why `renderToStaticMarkup` and not jsdom.** This project's register is explicit that a rendered
claim verified in jsdom is not verified. `renderToStaticMarkup` from `react-dom/server` is not a
simulation — it is the code path Astro uses to server-render a React island, and it returns a
string, which is precisely the artefact the assertion is about. A jsdom test would additionally be
checking jsdom's parser rather than React's escaping.

**Nothing renders a bullet yet.** There is no `/resume` page until Phase 5, so this component ships
unused. The gate in Task 2 is what stops Phase 5 reaching for a string instead. The verification
says so rather than implying coverage that does not exist.

**`set:html` matters even though this plan writes no `.astro` file.** It is Astro's spelling of the
same mistake, and Phase 5 writes the first pages. A gate added after those pages exist is a gate
added after the mistake became available to make.

**Then write `src/components/Bullets.tsx`.** It takes bullet strings and calls `parseBullet`

Hard constraints:

- **`parseBullet` is imported, not reimplemented.** The renderer holds no opinion about what `**`
  means.
- **No `dangerouslySetInnerHTML`, for any reason** — not for a bold run, not for an entity, not
  behind a comment asserting the input is trusted. This is the sink that produced the legacy hole.
- **Bold runs become `<strong>` elements; plain runs become text children.** React escapes text
  children by construction, and that mechanism is what this entire boundary rests on — so the
  component contains **no escaping code of its own**. Do not write an `escapeHtml` helper: a
  hand-rolled escaper is a second implementation of something React already does correctly, and it
  is the classic place to forget an entity.
- Keys on run elements. `index` is acceptable — runs are derived deterministically from a string and
  are never reordered.
- No Node-only imports; this renders during prerender in `workerd`.

**Design the payload so no degenerate renderer passes.** The load-bearing fixture is a **single
bullet** carrying both a genuine bold run and a script payload in its plain text, with both facts
asserted about the **same rendered output**:

```
run 0 (plain): "Reduced p95 <script>alert(1)</script> latency by "
run 1 (bold):  "40%"
```

- A renderer that passes everything through raw fails the escape assertion.
- A renderer that escapes everything, including the delimiters, fails the `<strong>` assertion.
- A renderer that returns its input fails both.

This is the same class of problem as the keyboard bug this project found — *"34 tests all focused
the first item, so 'the item picked up' and 'the first item' were always the same element."* Two
assertions over two fixtures would let one renderer be right about one and wrong about the other.
One fixture, two assertions, no overlap.

Assert on the string from `renderToStaticMarkup`, **positively and negatively**:
`toContain('&lt;script&gt;')`, `toContain('<strong>40%</strong>')`, `not.toContain('<script')`. The
negative alone is satisfied by rendering nothing.

**Assert the write half in the same file.** Feed the same string to `ResumeSchema` as a stored
bullet and assert it fails. That is what makes this one test rather than two, and it is what
criterion 3 literally asks for.

|----------|-------------|
| stored bullet → rendered DOM | The legacy hole in one line. Four call sites passed this string to `dangerouslySetInnerHTML` with no sanitiser in the repository. |
| `BulletRun.text` → React child | The escaping mechanism. It works because React escapes text children, so any code that bypasses that — a hand-rolled escaper, a sink — reopens the boundary. |
| Phase 5's `.astro` pages → the same content | The gate covers `set:html` before the first page exists, which is the only order in which that is cheap. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-03-07-01 | Elevation of privilege | the render boundary | mitigate | Runs become React elements and text children; no sink, no hand-rolled escaper. Proven by a fixture that a pass-through renderer and an escape-everything renderer each fail for opposite reasons. |
