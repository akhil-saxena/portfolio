<objective>
Make a malformed content file stop the build, with a message that tells the author what to fix, and
put every gate this phase produced behind one chained script and one CI job.

Purpose: criterion 2 is *"Committing a malformed `data/*.json` fails the build with a readable error
instead of shipping a broken site."* **Readable is the requirement**, and the phase prompt is
specific about what it excludes: *a stack trace naming a Zod path is not the same as telling the
author which file and which record.* `astro/zod`'s default issue message for a wrong type on
`experience[0].bullets[2]` is `"Invalid input: expected string, received number"` with
`path: ["experience", 0, "bullets", 2]` — accurate, and it names neither the file nor the company
whose bullet it is. The deliverable is the difference between those two.

**The premise most likely to be wrong here, and it must be measured before anything is built.**
`research/ARCHITECTURE.md` asserts that a module-scope `Schema.parse(raw)` in `src/lib/content.ts`
*"aborts `astro build` with the zod issue path — no bad page is emitted"* because *"Astro evaluates
this during prerender."* That is true **only if some prerendered page imports it**. Today nothing
does — `src/pages/index.astro` renders `StackProof` and no content, and there is no `/resume`,
`/photos` or `/work` until Phase 5. So the cross-file rules ADR-002 made load-bearing would sit in a
module that never executes, and the build would be green over a manifest with 39 orphaned photos.
The same doubt applies to the content collections: whether a `file()` loader schema failure *aborts*
`astro build` or is reported and survived is a behaviour to observe, not to cite.

**So the plan's first instruction is to find out**, with the real toolchain, before choosing a
mechanism. Everything downstream depends on the answer, and getting it from documentation is how
this project has produced gates that cannot fail.

Output: an unconditional build-time validation, a readable error formatter, typed content exports,
one chained gate script, one CI wiring, and a sweep proving every gate in the phase fails on the
defect it targets.
</objective>

<task type="auto">
  <name>Task 2: Prove a corrupt file stops a real build, four different ways</name>
  <files>test/content/build-fails-loudly.node.test.ts</files>
  <action>
This is criterion 2's evidence, and a unit test of the formatter is not it — that would assert a
string function returns a string, while the build never calls it. The test has to run a **real
`astro build`** with a **real corrupt file** and assert on the exit code and the output.

Write `test/content/build-fails-loudly.node.test.ts` in the `integration` project — it is the
Node-side project and the only one that can spawn a build. Note that the project's `globalSetup`
already builds and serves the site; this test spawns its own build with a mutated tree, so give it a
generous per-test timeout and make it restore the tree in a `finally` block, unconditionally, so a
failing assertion never leaves the repo corrupt.

Four cases. Each must assert **exit code ≠ 0** *and* that the combined stdout+stderr contains three
things: the **file name**, the **human identifier of the record**, and the **field**. Asserting only
the exit code proves the build broke, not that it broke legibly — and legibility is the requirement.

1. **Wrong type in the manifest.** `photos[12].order = "twelve"`. Output must name
   `portfolio_images.json`, that photo's `id`, and `order`.
2. **The ADR-002 rule.** A photo's `category` set to `"archtecture"` — a typo that is a perfectly
   valid string and is invisible to any per-file schema. Output must name the photo, the bad
   category, and `site_config`. **This is the case the whole phase exists for**; if the build is
   green here, `/admin/site` was deleted in exchange for nothing.
3. **A dangling peek id.** `home_config.peekIds[0]` set to `"does-not-exist"`. Output must name
   `home_config.json` and the id.
4. **An HTML tag in a bullet.** `experience[0].bullets[0]` set to
   `"Improved <script>alert(1)</script> conversion"`. Output must name `resume.json` and the company
   (`Brevo`) — this is the write-boundary half of criterion 3 arriving at the build, and it is the
   one place in the phase where all three of criteria 1, 2 and 3 are exercised by a single mutation.

**Add a fifth, positive case that is easy to skip and is the reason the other four mean anything:**
with the tree clean, the build exits 0. Without it, a mechanism that fails every build passes all
four negative cases.

**Two traps to avoid, both from this project's register:**

- Do not assert with `grep -c` semantics or a bare truthy substring check on a variable that could be
  empty — assert `output.includes(...)` on a non-empty captured string, and assert the string is
  non-empty first.
- Do not restore the data by re-running a migration script. Restore from a byte copy taken before the
  mutation, so a restore bug cannot silently rewrite content.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a git commit → a deployed site | The deploy workflow triggers on CI success and nothing else, so what CI enforces is what cannot ship. |
| `data/*.json` → the build | The only write path in Phase 3 is a text editor. This is where a bad edit is caught or is not. |
| the error message → the author | An unreadable failure is a failure that gets worked around, and a gate that gets worked around is worse than none. |
