<objective>
Build the check nothing in this repository can currently perform: **does the manifest tell the
truth about the bucket?**

Measured in `04-RESEARCH.md` §6, by planting it: a fully schema-valid 40th record whose four R2
objects do not exist passes `npx astro sync` at **exit 0**, reporting
`content set: PASS · checked: 40 photo(s) … rules run: RI-1…RI-6`, and passes `gate:origin` too —
because that gate checks the *origin* of every URL and never its liveness. `PhotoSchema`'s
`remoteUrl` refinement does the same. **The build would be green and the site would ship four
broken images.** PIPE-04's "the manifest is consistent with the bucket" has no enforcement at all
today, and building it is a Phase 4 deliverable.

The tool exists in shape: `scripts/migrate-photo-origin.mjs --verify` fetches every URL and
requires 200 + `image/webp`. It is scoped to the migration cohort (04-01 pins it there
deliberately). This plan generalises the liveness half into a standing verifier whose counts are
derived from the manifest it reads.

Purpose: criterion 3 — a job that fails partway must not leave the manifest claiming bytes that
are not there. This verifier is step 8 of the pipeline's ten-step order (04-09), sitting between
the R2 upload and the commit, so a failed upload becomes a failed job with no manifest change
rather than a green build over four 404s.
Output: `scripts/verify-photo-urls.mjs`, a network-free unit test of its pure parts, and a
`gate:liveness` npm script.
</objective>

<task type="auto">
  <name>Task 1: Write scripts/verify-photo-urls.mjs</name>
  <files>scripts/verify-photo-urls.mjs, package.json</files>
  <action>
Generalise the liveness half of `scripts/migrate-photo-origin.mjs --verify`. Header block, in the
house style, must state: what this catches that nothing else can (a schema-valid record pointing
at 404s — cite the §6 measurement), why the count is derived rather than asserted, and the
HEAD/GET rule below.

Behaviour:

  - Argv: `[manifestPath]`, `--only <photoId>` (check just that record's remote URLs), `--cache`
    (additionally require a `cache-control` header, and switch the request method to GET),
    `--concurrency <n>` defaulting to something modest like 8.
  - Read the manifest, refuse a non-array, refuse invalid JSON, refuse a missing file — each with
    a message naming the path. "There is nothing to check" is a failure, never a pass.
  - Assemble targets as `{ id, key, url }` over `REMOTE_URL_KEYS` for every record (or the one
    record `--only` names). Assert the assembled count equals
    `records.length * REMOTE_URL_KEYS.length` **and is greater than zero**, before issuing a single
    request. Under `--only`, additionally fail if the id matched no record — a verifier that
    checked zero URLs and printed "all OK" is the vacuous-gate failure this project has shipped ten
    times, and `migrate-photo-origin.mjs`'s own header says so.
  - Require every target's `url` to parse and have `.origin === IMAGE_ORIGIN` **before** requesting
    it. A record whose URL points somewhere else is a finding, not a fetch.
  - Request each target and require HTTP **200** with `content-type` starting `image/webp`.
    Report each failure as `<id>.<key>: <what was wrong> — <url>`.
  - **Method: HEAD by default, GET under `--cache`, and the reason is written in the header.** A
    HEAD against this origin returns `cf-cache-status: DYNAMIC` and **no `cache-control` header at
    all**, reproducibly, on objects a GET reports as `HIT` with `max-age=14400` (measured, three
    objects x three tries). HEAD is sufficient for status and content-type — that is what the 39
    records were verified with — but **any cache assertion must use GET or it will conclude the CDN
    is not caching and be wrong.** Make `--cache` switch the method, and make it impossible to
    assert on `cache-control` in HEAD mode.
  - On success print a report that names what it checked: the record count, the URL count, the
    origin, and the fact that `thumb` is excluded by construction. Not a bare `PASS`.
  - Exit 0 only when every target returned 200 + `image/webp`; otherwise exit 1 after listing every
    failure.

Wire it into `package.json` as `"gate:liveness": "node scripts/verify-photo-urls.mjs"`.
**Do not chain it into `gate:content`.** Write the reason in the SUMMARY and beside the script
entry if the format allows: `gate:content` is four offline gates that run on every build and in
every CI job; this one makes one network request per remote URL, so putting it on the build path
makes a CDN blip a red build. Its two real homes are step 8 of the pipeline job (04-09) and a
deliberate manual/e2e run (04-10).
  </action>

  </verify>
  <done>The verifier exits 0 over the committed manifest and reports a derived count (156 remote

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| committed manifest → live bucket | The manifest asserts that 4 objects exist per record. Nothing verified that until now. |
| verifier → public CDN | The verifier issues unauthenticated requests to an origin the project owns. No credential is involved and none should be. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-10 | Spoofing | `scripts/verify-photo-urls.mjs` origin check | mitigate | Parse each URL and require `.origin === IMAGE_ORIGIN` **before** requesting it, so the verifier never fetches an attacker-chosen host and never reports a foreign 200 as proof of liveness. |
| T-04-11 | Repudiation | The verifier's PASS report | mitigate | Task 3 step 2: three separate "nothing to check" cases must exit 1. A PASS must name the derived record and URL counts, so a report over zero targets is visibly impossible. |
| T-04-12 | Denial of service | Fan-out of one request per remote URL | mitigate | Bounded `--concurrency` (default 8), and the gate is deliberately NOT chained into `gate:content`, so it is not on the build path where a CDN blip would red every push. |
| T-04-13 | Information disclosure | Cache-header assertions | mitigate | `--cache` forces GET. HEAD returns `DYNAMIC` and no `cache-control` on this origin (measured), so a HEAD-based cache assertion reports a result it did not measure. The script makes the wrong combination unrepresentable. |
| T-04-SC | Tampering | npm/pip/cargo installs | mitigate | This plan installs nothing. `package.json` is edited only to add a `scripts` entry; no dependency is added, so the Package Legitimacy Gate does not apply here — it applies in 04-04. |
</threat_model>
