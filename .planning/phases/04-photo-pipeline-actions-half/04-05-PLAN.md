<objective>
Turn derived image assets plus validated dispatch inputs into **one manifest record that the
Phase 3 content gate accepts**, and define what a re-run does.

This is a rewrite, not a port. Measured in `04-RESEARCH.md` §6 by planting exactly what the legacy
`processImage()` returns: `npx astro sync` exits 1 with **seven findings in four classes** —
`alt` missing, all four `urls.*` on the retired `r2.dev` origin, `categoryOrder` missing, and
`tags` present-and-forbidden. Every RI rule is then listed as **not run**, because the file did not
satisfy its own schema. That is the porting delta, exactly, and nothing else about the legacy
imaging logic is wrong.

The producer is **pure**: no network, no filesystem, no git, no sharp. It takes an assets object
and returns a record; it takes a manifest and a record and returns a new manifest. That is what
makes validation-before-side-effects possible in 04-09's ten-step order — steps 1–6 have no side
effect, and step 6 is `astro sync`, the 1.7-second full content gate that needs no `.env`.

Purpose: PIPE-01 (the record), PIPE-03 (a re-run adds no duplicate), CONT-05 (a different byte
sequence gets a different URL).
Output: one pure module, two unit suites, and one integration proof that runs the real gate.
</objective>

The record `PhotoSchema` requires — `z.strictObject`, so an unknown key is a failure, not an
addition:
  id, title, alt, category, date, exif{6 nullable non-optional}, urls{4 remote + thumb},
  order (positive int, unique across the manifest — RI-5),
  categoryOrder (positive int, unique within its category — RI-6),
  dimensions{width,height}
  optional: place, description, focalPoint (no zod default — parse() must not materialise it)
  forbidden: tags (z.never().optional(), with the OD-3 rationale in the error message)

`alt`'s four superRefine rules: non-empty after trim; not equal to `title` compared case- and
whitespace-insensitively; must not open with `image of` / `photo of` / `picture of`; must not
contain `[AKHIL-`.

The six RI rules (`src/schemas/content-set.ts`) a new record can break:
  RI-1  photo.category must exist in site_config ids — EXACT comparison, no case transform
  RI-5  photo.id and photo.order each unique across the whole manifest
  RI-6  categoryOrder unique within its category
  (RI-2, RI-3, RI-4 are not reachable by ADDING a record — only by deleting one.)

Serialisation, measured: the committed manifest is `JSON.stringify(x, null, 2)` **plus a trailing
newline** (57,345 bytes with it). The legacy writer omitted the newline, so a legacy-shaped write
reverts 03-01's fix and produces a spurious one-line diff on the closing `]`.

<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: OD-4 — what "re-running the same job" should do</name>
  <decision>The semantics of idempotence. Criterion 2 says only "adds no duplicate manifest entry",
which three different implementations satisfy.</decision>
  <context>
Measured: a naive duplicate append **is** caught, but only after the manifest is written —
`npx astro sync` exits 1 with `[RI-5] indices 39, 40: duplicate photo id`, `[RI-5] duplicate
global order value 40` and `[RI-6] categoryOrder 9 is used by … and …`. So the safety net exists.
It is a net, not a design: it fires after the file is on disk. If the producer validates before
uploading and committing, this becomes a job failure with no side effects, which is what PIPE-03
should mean.

The legacy dispatch entrypoint did the third thing: `if (existingIds.has(entry.id)) { console.error
("Duplicate ID"); process.exit(1); }` — a re-run **fails** rather than no-ops.
  </context>
  <options>
    <option id="OD-4-A">
      <name>A (recommended) — upsert keyed on `id`, exit 0</name>
      <pros>A re-run recomputes the record and replaces it in place, **preserving the existing
`order` and `categoryOrder`**. Retry after a partial failure becomes the ordinary path rather than
a manual cleanup, which is exactly what criterion 3 needs: a job that failed between the R2 upload
and the commit can simply be re-dispatched.</pros>
      <cons>Carries a caveat that must be implemented, not just noted: **an upsert must NOT
renumber `order`.** Renumbering would reorder the gallery as a side effect of a retry, which is a
visible change to reviewed data caused by an operational action.</cons>
    </option>
    <option id="OD-4-B">
      <name>B — detect and no-op, exit 0</name>
      <pros>Cheaper and simpler; the manifest is untouched on a second run.</pros>
      <cons>A re-run after a **partial** failure then cannot repair the R2 side — the record is
already there, the bytes may not be, and the operator has no in-band way to fix it.</cons>
    </option>
    <option id="OD-4-C">
      <name>C — legacy behaviour: exit 1 on a duplicate id</name>
      <pros>Satisfies criterion 2 literally and loudly.</pros>
      <cons>Makes recovery a human job every time, and turns the most common operational event
(re-dispatch after a transient failure) into an error.</cons>
    </option>
  </options>
  <resume-signal>Reply `OD-4: A`, `OD-4: B` or `OD-4: C`. If A, confirm the caveat explicitly:
a re-run preserves the existing `order` and `categoryOrder` rather than recomputing them.</resume-signal>

    RED first. Every one of these is a failing test before a line of `photo-record.mjs` exists.

    Ranking:
    - `nextOrder(manifest)` returns `max(order) + 1`; over an empty manifest it returns 1 and does
      not return `NaN` or `-Infinity + 1`.
    - `nextCategoryOrder(manifest, category)` returns `max(categoryOrder within that category) + 1`;
      for a category with no records it returns 1.
    - Both are derived from the manifest passed in, never from a cached read. (Pitfall P-5: two runs
      that both read `maxOrder = 39` both write `order: 40`.)

    Upsert (implement whichever OD-4 option was chosen; these are option A's):
    - Inserting a new id increases `manifest.length` by exactly 1 — asserted BEFORE any claim about
      the second run, so "no duplicate" cannot be satisfied vacuously by an insert that never
      happened.
    - Running the upsert a second time with the same id leaves `manifest.length` unchanged.
    - The second run preserves the FIRST run's `order` and `categoryOrder` byte-for-byte, even
      though the manifest's maxima have not moved.
    - The second run DOES update the fields that legitimately changed — the urls, the hash, the
      dimensions, the exif — so an upsert is a repair, not a no-op-in-disguise.
    - The upsert never mutates its input array or any record object in it.
    - Every other record's `order` and `categoryOrder` are unchanged after an upsert. Assert this
      over the whole manifest, not on a sample.

    Record shape:
    - `buildRecord(...)` output passes `PhotoSchema.safeParse` — and the test asserts
      `success === true` and, on failure, prints `error.issues` so a regression names the field.
    - `id === photoIdFor({category, slug})` and matches `/^[a-z0-9-]+$/`.
    - `urls` has exactly the five keys; the four remote ones each parse to `.origin ===
      IMAGE_ORIGIN`; `thumb` starts with the `data:image/webp;base64,` prefix.
    - `exif` has exactly six keys, all present, each `string | number | null`.
    - `tags` is absent — not empty, absent. Assert `'tags' in record === false`.
    - `focalPoint` is absent unless supplied. `parse()` must not materialise it.
    - Given a source with no EXIF at all, the record still carries a complete six-key all-null
      `exif` object and still passes the schema.

    Versioned keys (CONT-05):
    - Two different variant buffers produce two different `urls.original` values.
    - The SAME buffer produces the same value on a second call — content-addressed, not random.
    - Re-running with new bytes leaves the previous record's URLs recoverable from git history and
      does not reuse the old URL, so the old URL's bytes are never overwritten.
    - Every one of the four `VARIANTS` gets its own hash from its own emitted buffer, not one hash
      from the source. (The variants differ; a single source hash would make `-lg` and `-sm` share
      a version and defeat the point for three of the four.)

    Serialisation:
    - `serialiseManifest(manifest)` ends with exactly one `\n`.
    - `serialiseManifest(JSON.parse(readFileSync(committedManifest)))` is **byte-identical** to the
      committed file. This is the regression guard against the legacy writer's missing newline, and
      it is checkable today against a 39-record file.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| dispatch inputs → committed record | `category`, `title`, `alt`, `place` come from a caller and end up in a file on `main`, and in Phase 5 in rendered HTML. |
| derived assets → committed URLs | Hashes and dimensions come from a decode of untrusted bytes and become permanent addresses. |
| producer → manifest on disk | The producer is the only thing that decides `order` and `categoryOrder`, which are global and per-category uniqueness constraints. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-17 | Tampering | `upsertRecord` rank derivation | mitigate | Ranks derived from the manifest passed in, never cached; asserted over the whole manifest that no other record's rank moved. Pitfall P-5 (two runs both reading `maxOrder = 39`) is closed operationally by 04-06's re-derive-after-fetch retry loop. |
| T-04-18 | Elevation of privilege | `alt` / `title` / `place` reaching rendered HTML | transfer | These are attributes and text, escaped at Phase 3's render boundary and covered by `gate:sinks`. This plan validates them against `PhotoSchema` before any side effect; the render-side control is Phase 5's, not this plan's to duplicate. |
| T-04-19 | Spoofing | Produced `urls.*` | mitigate | Composed only through `publishedUrl` from `IMAGE_ORIGIN`; asserted by origin **equality** (a `startsWith` is defeated by `https://HOST.evil.test/` and `https://HOST@evil.test/`). No hostname literal in this module. |
| T-04-20 | Repudiation | The RI census | mitigate | Task 3 case 4 pins the measured behaviour that a schema failure suppresses the RI census, so a future reader cannot mistake a missing `✖ [RI-n]` line for a rule that passed. |
| T-04-21 | Information disclosure | `PhotoSchema`'s `z.strictObject` | mitigate | An unknown key is a failure, not an addition, so a caller cannot smuggle an extra field into a committed record. `tags` is spelled out as `z.never()` so the refusal carries the decision. |
| T-04-SC | Tampering | npm/pip/cargo installs | mitigate | This plan installs nothing. Dependencies are added only in 04-04, behind the Package Legitimacy Gate. |
