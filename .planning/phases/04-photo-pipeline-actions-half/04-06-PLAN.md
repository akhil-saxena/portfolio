<objective>
Make the pipeline's own write safe against a concurrent human edit, and write down the contract the
other side of PIPE-05 will have to honour when it exists.

Verified on the legacy branch: `src/components/admin/DeployButton.tsx:86` sends
`baseSha: "latest"`, and `src/app/api/deploy/route.ts` reads
`if (baseSha !== "latest" && currentSha !== baseSha) { /* 409 */ }` — so the guard was **disabled
in production**, exactly as `CLAUDE.md` and `PROJECT.md` describe. `PROJECT.md:127` already
diagnoses why someone disabled it: HEAD-comparison is too strict, the photo pipeline commits
constantly, so it 409s unrelated edits.

The admin does not exist yet, so Phase 4 can build exactly one side of PIPE-05 — and criterion 4 is
still testable today, because "a concurrent manual edit" is just a human `git push`.

**The recovery is re-derive, never rebase.** A textual `git rebase` of an appended JSON array
element is a conflict waiting to happen, and it resolves `order` incorrectly **even when it
succeeds** — the appended record keeps the rank it was given against the old maxima while another
record now holds it. That is pitfall P-5, and it is why the retry re-runs the upsert against the
freshly fetched manifest rather than replaying a diff.

Purpose: PIPE-05 and criterion 4.
Output: a publish module with a bounded retry, an integration proof against a real local bare
repository, and the written contract for Phase 7.
</objective>

Cited API semantics, for the contract document — not used by this module, which pushes with git:
  `PUT /repos/{owner}/{repo}/contents/{path}`: `sha` is "the blob SHA of the file being replaced",
  required when updating, and a mismatch returns **409 Conflict**.
  `PATCH /repos/{owner}/{repo}/git/refs/{ref}`: `force` defaults to false — "make sure the update
  is a fast-forward update … Leaving this out or setting it to false will make sure you're not
  overwriting work". So even with `baseSha` bypassed, a commit landing between the ref read and
  the PATCH is still refused; that narrow last line of defence is what the legacy route mapped
  to 409.

GitHub Actions concurrency, and the precedent already in this repository — `deploy.yml`:
  concurrency: { group: deploy-main, cancel-in-progress: false }
with the reason written beside it: "Deploys QUEUE, they do not cancel … cancelling a run
mid-publish is the specific way a Worker and its static assets end up at different versions."
`ci.yml` does the opposite (`cancel-in-progress: true`) and says why. The photo pipeline follows
`deploy.yml`: **queue, do not cancel** — 04-08 wires it.
</interfaces>

**Shell discipline.** Interactive shell is **zsh**; Actions is **bash**. No `${PIPESTATUS[0]}`
(zsh spells it `${pipestatus[1]}`), no `R=$?`, no `( cmd && R=0 || R=1 )`. Capture as
`if cmd; then R=0; else R=1; fi`. Every `git` invocation in the module uses `execFile` with an
argv **array**, never a shell string — a filename or a branch name interpolated into a shell
string is a command-injection surface and there is no reason to accept one here.
</context>

    - A clean fast-forward push succeeds on the first attempt and reports `attempts: 1`.
    - When the remote has moved, the push is rejected; the module fetches, re-reads the fetched
      file, calls the caller's `rederive` callback with the fetched content, re-writes, re-commits
      and pushes again.
    - The foreign commit is **still present** in the remote's history after a successful retry.
      Assert it by SHA, not by file content — content could coincide.
    - `rederive` is called exactly once per retry and **is called with the fetched manifest**, not
      with the stale one. Assert the argument, or the whole retry is theatre.
    - After `PUBLISH_RETRY_LIMIT` failed attempts the module throws `PublishConflictError` naming
      the branch, the remote head SHA and the number of attempts made.
    - The module never invokes `rebase`, never passes `--force` or `--force-with-lease`, and never
      calls `reset --hard` on a branch it did not create. Assert this by inspecting the argv of
      every `git` call the module makes, not by reading the source.
    - A validation failure inside `rederive` aborts the loop immediately — it does not consume the
      retry budget and does not push a record the gate rejected.
  </behavior>
  <action>
Write `scripts/lib/git-publish.mjs`.

`publishManifest({ repoDir, branch, filePath, message, rederive, retryLimit })`:
  - Configure the committing identity explicitly for the invocation (`-c user.name=… -c
    user.email=…`) rather than relying on the runner's global config, and take both from the
    caller so 04-08 can set them from the workflow.
  - Stage only `filePath`. Never `git add -A` — the runner's working tree may contain build output,
    `node_modules` symlinks or a downloaded staging object, and a pipeline that commits whatever it
    happens to find is a supply-chain surface, not a convenience.
  - Commit, then push to `branch`.
  - On a **non-fast-forward rejection specifically** (match the remote's rejection, do not treat
    every non-zero git exit as a conflict — an auth failure and a conflict must not share a code
    path, and a missing credential must fail the job rather than silently retry three times):
      1. `git fetch origin <branch>`
      2. reset the local branch to the fetched tip — the pipeline's own commit is discarded, not
         rebased. Its content is about to be recomputed.
      3. read `filePath` **from the fetched state**
      4. call `rederive(fetchedContent)` → new content. This is where 04-05's upsert recomputes
         `order` and `categoryOrder` against the NEW maxima.
      5. write, stage, commit, push again.
  - Bounded at `retryLimit` (default `PUBLISH_RETRY_LIMIT` from the contract module). On exhaustion
    throw `PublishConflictError` with the branch, the remote head and the attempt count in the
    message. **Fail loudly**: criterion 4 says one side "retries or reports a conflict", and a
    silent give-up is neither.
  - Log each attempt with its outcome. Never log the remote URL if it carries a credential; log the
    branch and the SHA only. (ASVS V7: a failed call must not echo the credential — the legacy
    routes log `res.status` and a generic message, never the token.)

Header must state, in the file: why re-derive and not rebase (P-5, with the `order` example), why
the retry is bounded, and that a credential failure is not a conflict.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Actions runner → `main` | The runner holds a token able to push to the default branch. Anything it commits is what the site ships. |
| remote state → local retry | The retry reads content the pipeline did not write and recomputes ranks against it. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-22 | Tampering | `publishManifest` push | mitigate | Never `--force`, never `--force-with-lease`, never `rebase`. Assert the prohibition by inspecting the argv of every `git` call the module makes, not by reading the source. The remote's own fast-forward check stays the guard. |
| T-04-23 | Tampering | `git add` scope | mitigate | Stage only the single `filePath`. Never `git add -A` — a runner working tree can hold build output, a symlinked `node_modules` and a downloaded staging object, and committing whatever is present is a supply-chain surface. |
| T-04-24 | Elevation of privilege | `execFile` argv | mitigate | Every git invocation uses an argv array, never a shell string. A branch name or path interpolated into a shell string is a command-injection surface with no upside. |
| T-04-25 | Information disclosure | Retry logging | mitigate | Log branch and SHA only; never the remote URL, which can carry a credential. ASVS V7, and the pattern the legacy routes already followed (`res.status` and a generic message, never the token). |
| T-04-26 | Denial of service | Unbounded retry against a busy branch | mitigate | Bounded at `PUBLISH_RETRY_LIMIT`; exhaustion throws `PublishConflictError` naming the branch and the attempt count. `concurrency: { cancel-in-progress: false }` in 04-08 serialises pipeline runs against each other so the loop contends only with humans. |
