<objective>

**CONSTRAINT FROM 04-03, MEASURED — do NOT switch the step-8 liveness probe to GET.**

My brief to 04-03 said "every liveness assertion must use GET, because HEAD lies about caching."
That is right for **cache** assertions and **wrong for liveness**, and 04-03 measured why rather than
following it:

- `HEAD` returns `cf-cache-status: DYNAMIC` — it is never served from the edge, so it actually asks R2.
- `GET` can be answered by the edge (`HIT` / `REVALIDATED` / `EXPIRED`).

So a GET **cannot distinguish "the object exists" from "the object was cached before the upload
failed"** — a false pass exactly at pipeline step 8, on a mutable key, which is the one place this
phase cannot afford one. 04-03 found a live URL answering `HEAD 404` / `GET 200` from different colos;
that specific example did not reproduce on a later probe, but the cache-status asymmetry did and is
the load-bearing part.

**Therefore:** step 8 probes with **HEAD**. Cache behaviour, if this plan asserts any, uses **GET**.
The two are different questions and take different methods. `scripts/verify-photo-urls.mjs` already
encodes this with a frozen mode table whose invariant makes the module **refuse to load** if the
table is mutated to assert `cache-control` over HEAD — reuse it rather than re-deriving.


Assemble the job: **derive → validate → upload → verify → commit → delete**, in that order, with
the line above which nothing has a side effect written into the source.

```
1  read dispatch inputs (validated in 04-08)
2  GET the staged object out of R2                              [read-only]
3  sharp: source metadata + 4 variants + 40px thumb; EXIF        [pure, in memory]
4  hash each emitted variant -> compose the R2 keys and URLs     [pure]
5  read data/portfolio_images.json; derive ranks; upsert         [local write only]
6  astro sync   <- 1.7s, 5 schemas + 6 RI rules; exit 1 stops the job
   ------------------ NOTHING ABOVE THIS LINE HAS A SIDE EFFECT ------------------
7  PUT the variants to R2
8  liveness verify: GET every URL in the new record, 200 + image/webp
9  git commit + push, with the bounded re-derive-and-retry loop
10 DELETE the staged temp/ object                                [the once-only token]
```

Every criterion this order serves, stated per step:

- **Criterion 3 (partial failure).** A crash before step 7 leaves nothing changed anywhere. A crash
  between 7 and 9 leaves **orphan bytes in the bucket** — invisible, harmless, and swept by the
  same lifecycle machinery — but never an orphan *record*. The forbidden direction is a manifest
  entry with no bytes, which §6 proves no existing gate can catch: a schema-valid record over four
  404s passes `astro sync` at exit 0 reporting `PASS · 40 photo(s)` and passes `gate:origin` too.
- **Criterion 2 (idempotence).** Step 10 last makes the `temp/` key a once-only token: a re-run
  after success finds nothing to fetch and exits cleanly. A re-run after a step-7 failure re-does
  everything from a clean read.
- **Criterion 1.** Step 6 is the schema-valid guarantee, step 8 is the "the variants really are in
  R2" guarantee, step 9 is the commit.

Purpose: PIPE-01, PIPE-03, PIPE-04.
Output: the entrypoint, an R2 I/O module, the workflow's processing steps, and an integration
suite that injects a failure at each boundary and asserts what survived.

**T-04-47's only executable enforcement is this probe, so it must be a script, not a `node -e`
one-liner.** (The previous version was a one-liner, and my W2 repair text was pasted *inside* its
command string — the explanation became the command. A one-liner is what invited that; a file does
not.)

Write `scripts/lib/r2-fail-closed.probe.mjs`. It proves the R2 module **fails closed** — CLAUDE.md's
"a missing configuration denies rather than degrades" — and it must not pass for the wrong reason.

`scripts/lib/r2.mjs` must also export **`REQUIRED_ENV`**: the array of variable names it requires.
This is the one piece the probe cannot know at plan time, because it differs between OD-5's two
branches (S3 SDK vs `wrangler`), and hardcoding a guess is how a probe ends up asserting nothing.

The probe:

1. Seed **every** name in `REQUIRED_ENV` to a valid-looking dummy, then import the module once to
   read `REQUIRED_ENV`. **Refuse with a non-zero exit if `REQUIRED_ENV` is empty** — an empty list
   would make every subsequent check vacuous. This is the anti-vacuity clause.
2. For **each** name in turn: re-seed all of them, empty **exactly that one**, cache-bust the import
   (`await import(mod + '?t=' + name)`), and require the module to **throw** with a message that
   `.includes(name)`.
3. Fail loudly, naming the variable, if the module instead **imports cleanly** (fails open) or throws
   without naming the emptied variable.

Why per-variable rather than one shot: the local shell has **no** `R2_*` or `CLOUDFLARE_*` set at all
(`.env` and `.dev.vars` hold only `CF_ACCESS_TEAM_DOMAIN` and `CF_ACCESS_AUD`), so a probe that
empties one variable and accepts any message matching `/R2_|CLOUDFLARE_/` passes because *some* other
variable is absent — never exercising the empty-string branch it claims to test.


Implement `getStagedObject`, `putVariant` and `deleteStagedObject` using whichever mechanism OD-5
selected in 04-04 — `@aws-sdk/client-s3` with the five existing `R2_*` secrets, or
`wrangler r2 object get/put/delete` with `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID`.

Rules, all of them load-bearing:

  - **The module composes no keys.** It takes a key and does I/O. `publishedKey` and
    `STAGING_PREFIX` live in `src/lib/photo-pipeline.ts`; a second opinion here is how the delete
    step ends up pointed at a different object from the get step.
  - **A missing credential fails the job.** `CLAUDE.md`: "auth fails closed … missing configuration
    denies rather than degrades." Assert every required environment variable is present and
    non-empty **at module init**, and throw naming which one is missing. Do **not** guard binding
    access the way the legacy Worker routes did — that pattern exists because
    `getRequestContext().env` is unavailable under `next dev`, and it is the wrong shape here: this
    runs on a Node runner where an absent credential is a real failure, and a guard would let the
    job skip the upload and commit a record anyway. That is the single worst outcome this phase can
    produce.
  - **Never echo a credential.** On an upstream failure, log the status and a generic message, and
    the key — never the token, never the endpoint with credentials embedded. The legacy routes set
    this precedent deliberately.
  - `putVariant` sets `ContentType: 'image/webp'` and `CacheControl: OBJECT_CACHE_CONTROL`. The
    legacy `PutObjectCommand` set **no** `CacheControl`, which §4 shows is exactly why the zone
    default applies and why a re-upload serves stale bytes for four hours.
  - Bound the work: at most one in-flight write per key (R2 documents 1 write/s per key), and a
    retry on a transient 5xx that is bounded and logged. A 4xx is not retried.
  - `deleteStagedObject` is idempotent: deleting a key that is already gone is success, not an
    error. A re-run after a completed job must exit cleanly, which is what makes the `temp/` key a
    once-only token.
  - State the tier in the header: **this module runs on the Actions runner and never in `workerd`.**
    The Worker's `PORTFOLIO_BUCKET` binding is a read/serve path; the pipeline is not in the Worker
    and does not use it.

     **the manifest on disk is byte-identical to before the run**, no puts, no deletes. This is the
     one that proves the restore in step 6 works; without it a rejected record sits in the working
     tree waiting for the next thing that commits.
  4. **Throw in step 7 after two of four puts.** Exit non-zero. **The manifest is byte-identical**
     (the forbidden direction — a record with no bytes — did not happen), exactly two objects exist
     in the fake bucket (orphan bytes, which is the permitted direction), and the staged object is
     **not** deleted, so a re-run can repair.
