  <name>Task 1: The schema fields and the migration, landed together in one commit</name>
  <files>src/schemas/projects.ts, data/projects.json, scripts/migrate-project-copy.mjs</files>
  <action>
    **This task lands the schema change and the data change in a SINGLE commit, and that is not a
    style preference.** Wave 1 runs four other plans concurrently in this working tree. A schema
    that requires `status` while `data/projects.json` has none makes `npm run build` red for every
    wave-mate, and the `astro:config:done` content gate fires on `astro check` and `astro sync`
    too. Write the script, run it, verify, and commit all three files at once.

    **`src/schemas/projects.ts`** — add to `ProjectSchema`, keeping it `z.strictObject`:

      status:   z.enum(['live', 'maintained', 'archived'])
      oneLiner: z.string().min(1)

    and keep `description` exactly as it is, including the `LITERAL_COMPONENT_FIGURE` refusal.

    Both are REQUIRED, not optional — all five records get a value, and "absent" would be a second
    way of saying something the data never means. Follow the file's own convention: each new field
    carries a comment naming the decision (D-45 for the status vocabulary, §13.1 for the two copy
    slots) and stating why the rule is where it is.

    Do NOT put the 60–110 / 120–200 budgets in the schema. Measured: the stored design-system
    one-liner is 116 characters because the token is 19 characters longer than the figure it
    replaces, and it resolves to 97. A zod refinement on the stored string would refuse correct
    data. The budget belongs to the resolved string and lives in task 3.

    Do NOT add a rule tying `status` to `badges[]`. §10.2: `badges[]` is a link list, and the
    coincidence that cairn's first badge reads "Live" is exactly the confusion this field ends.

    **`scripts/migrate-project-copy.mjs`** — plain node, runnable as
    `node scripts/migrate-project-copy.mjs`, no bundler-only specifiers:

      - Parse `.planning/phases/00-design-ideation/00-COPY/one-liners.md` as the source. Extract,
        per `## <id>` section, the `- one-liner:`, `- card:` and `- badge:` lines. THROW if the file
        yields fewer sections than `data/projects.json` has records, or if any section is missing
        any of the three lines, naming the id and the line. A migration that silently skipped a
        record would leave a schema-required field absent and read as a schema bug.
      - Map `badge: Live|Maintained|Archived` → `status` lowercase. THROW on any other value.
      - Write `oneLiner` from `one-liner:` and `description` from `card:`, applying the two token
        substitutions above and NOTHING else. Assert after substitution that neither string still
        matches `/\b\d+[- ]component/i` — if it does, the schema will refuse it and the operator
        should hear it from the migration, not from a build three steps later.
      - IDEMPOTENT: a second run must produce a byte-identical file. Do not measure idempotence
        with `git diff --quiet` — 03-04 shipped exactly that and it read the changes the first run
        had just made and reported "not idempotent" on correct code. Measure it in-process:
        serialise, run the transform again over its own output, and compare the two strings.
      - Preserve key order and 2-space JSON formatting so the diff is the copy change and nothing
        else.

    Run it. Then run `npm run build` and confirm the content gate reports a clean set.
  </action>

  </verify>
