<objective>
Turn the raw EXIF corpus into human names, and make an unknown string a build failure rather than a
guess or a model code on the page.

Purpose: PUB-08 exists because the manifest stores `NIKON CORPORATION NIKON D5300`. §9.5 measured
the whole corpus and it is closed and small — five distinct non-null camera strings and four
distinct non-null lens strings. It also measured why this is a lookup table and not an algorithm:
a prefix-stripping, title-casing prettifier gets the Nikon right and leaves `SM-N970F`, `AC2001`
and `ILCE-7CM2` unchanged, and **three of the five non-null camera strings are model codes no
algorithm can decode.** Rendering the raw code ships `SM-N970F` to a reader; rendering a guess
ships a lie; refusing the build is the only option that does neither, and the table is a two-line
edit.

PUB-07's rule lives here too, because it is a property of the row list rather than of any one page:
render a row only if its value is non-null, render the block only if at least one row survives.

Output: one pure module, one build gate, one unit suite.
</objective>

  <files>scripts/assert-exif-display-coverage.mjs</files>
  <action>
    A gate that iterates every record in `data/portfolio_images.json` and, for each non-null
    `exif.camera` and `exif.lens`, asks the table whether it has an entry. Any miss fails, naming
    **the value and the photograph id** — both, because the value alone does not tell you which
    file to look at and the id alone does not tell you what to add.

    Mechanics that are not optional here:

      - **Derive every count.** Print the number of records scanned, the number of distinct camera
        strings and the number of distinct lens strings, all computed from the file. Do not write
        40, 5 or 4 anywhere. 03-01's `--verify` hardcoded 39 and STATE.md flagged it; 04-09 then
        wrote a new hardcoded count and the first real photograph turned `main` red. The manifest is
        already at 40.
      - **Refuse to pass on nothing.** Exit 1 if the manifest is missing, is not an array, or holds
        zero records, with a message saying so. An empty array makes every per-record rule pass
        without reading a record — the exact vacuity the schemas' own `.min(1)` guards exist for.
      - **Read the tables from `src/lib/exif-display.ts`, do not restate them.** The module is TS
        with extensionless relative imports elsewhere in `src/`, so a plain `node script.mjs` may
        not import it. Two acceptable mechanisms, in order: (a) `node --experimental-strip-types`
        if this repo's Node (22.22.3, per `.nvmrc`) resolves the module cleanly; (b) call
        `displayCamera`/`displayLens` through a tiny vitest test instead and make THAT the gate,
        wired as a test rather than a script. Measure (a) first and record the result; if it fails,
        take (b) and say so in the file header. What is NOT acceptable is a second copy of the two
        tables in the gate — a gate that agrees with itself proves nothing, which is what the
        `THUMB.dataUriPrefix` note in `src/lib/photo-pipeline.ts` records about an earlier attempt.
      - Report with `process.stdout.write`.
      - Do not wire into `package.json`; 05-14 owns that.
